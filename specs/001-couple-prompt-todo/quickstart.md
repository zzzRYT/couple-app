# 구현 단계 검증 시작 가이드

이 문서는 후속 구현자가 검증 환경을 준비할 때 쓸 설계 기반 체크리스트다. 현재 저장소에는 앱/API 구현물이 없고 이 계획 작업에서 명령을 실행하거나 테스트를 추가하지 않았다. 실제 명령과 예상 출력은 구현 선택 및 앱 생성 이후 확정한다.

## 선행 준비

1. 소유자가 Supabase 프로젝트(무료 플랜, 서울 리전; 무료 프로젝트는 비활동 시 일시 정지됨), Auth OAuth 자격 증명, Apple/Google **개인** 개발자 계정, Kakao 앱, Expo/EAS 프로젝트를 만든다. bundle ID/applicationId 제안은 `com.jinjinstar.mopiru`(**이름 확인이 끝나기 전에는 스토어에 등록하지 않는다**), 지원·개인정보 처리방침 페이지는 `mopiru.jinjinstar.com`(소유자가 만들어야 한다).
2. Anthropic **Console API 키**(소유자의 Claude Max 요금제에 포함된 월 $100 API 크레딧으로 충당; 이 프로젝트 전용 Console workspace를 만들고 지출 한도를 둔다)를 개발자 로컬 비밀 환경과 서버 Edge Function secret store에 각각 보관한다. 포함 크레딧은 결제 주기마다 지급되고 남은 것은 주기 끝에 소멸하며 잔액이 0이면 다음 지급 때까지 요청이 멈춘다. 소유자의 채팅 로그인·Claude Code 구독 한도·OAuth 토큰은 앱이나 서버에 쓰지 않는다. 키를 `.env` 추적 파일, 로그, 앱 설정/번들, 문서나 채팅에 넣지 않는다.
3. 실제 초대 코드를 포함하지 않는 테스트 계정 2개와 공간 1개를 준비한다. 스토어 심사 전 샘플 공간은 고정 seed로 별도 유지한다.
4. 로컬 및 CI에서 공유 `scene-contract` 패키지, API mock/fixtures, Supabase local stack 사용법을 구현 단계에서 마련한다.
5. (계정 삭제, 출시 전) 소유자가 Apple 로그인 서비스 키(토큰 해제용)와 카카오 앱의 연결 끊기 권한·서버 비밀 키를 서버 비밀 저장소에 준비하고, `mopiru.jinjinstar.com/delete-account` 페이지를 만든다. 개발·테스트에서는 공급자 호출을 모의로 대신한다(실제 호출은 G18에서 수동 확인).

## 주요 검증 흐름

### A. 장면 문서·보호 영역

`contracts/room-scene.schema.json` fixture로 아래 사례를 검증한다.

- 유효한 장면: 서로 다른 허용 ID, 오브젝트 16개 이하, 텍스트 3개 이하.
- 경계 실패: 17번째 오브젝트, 네 번째 문구, 0보다 작거나 1보다 큰 좌표, 음수/범위 초과 회전, 길이 초과 텍스트.
- 보안 실패: 임의 필드, URL, SVG/HTML, script, 이벤트 속성, 알 수 없는/은퇴된 asset ID.
- 기하 사례: 회전 bounding box, 장면 가장자리 밖 노드, 상단·하단 시스템 안전 영역, 실제 네이티브 컨트롤과 D-day 뷰 침범.
- 기기 사례: 좁은/넓은 휴대전화 비율, 큰 글자 접근성 설정, 한글 줄바꿈, 텍스트 대비 하한.
- 언어별 사례: `ko-KR`, `en-US`, `ja-JP`에서 날짜와 숫자 표기, 각 언어의 D-day 문구, 실제 번역·pseudo-localization 텍스트 확장, 줄바꿈과 긴 라벨.
- 마스코트 사례: 새 방에 기본 마스코트 1개, 마스코트 포함 오브젝트 16개 경계, 마스코트에 붙은 상태 필드(`mascotState`, 착용·색·표정·포즈)와 중복 마스코트 거부, base character 교체·변형 요청 거절.
- room theme 사례: `day`, `night`, `follow_time` 설정과 각 낮/밤 variant의 배경/팔레트/asset ID 검증.

예상: 같은 scene fixture가 서버와 앱에서 같은 검증 결과를 낸다. 위험한 후보는 미리보기나 저장 전에 거부되고 기존 버전은 그대로다.

### A2. 언어 전환과 줄바꿈

- 기기 언어에서 시작하고 설정에서 `ko-KR`, `en-US`, `ja-JP`를 각각 선택해 모든 화면 문자열, 날짜·숫자와 D-day wording 전환을 확인한다.
- 실제 일본어 번역 및 각 언어의 pseudo-localized 긴 문자열을 인증, 초대, 설정, 프롬프트, 오류, 확인 패널에 표시한다. 좁은 화면과 큰 글자에서도 text expansion이 clipping을 만들거나 고정 컨트롤을 가리지 않는지 확인한다.
- 세 launch language 모두로 prompt를 각각 작성한다. AI 입력을 허용하고 커플 작성 문구가 저장 값에서 번역/변경되지 않는지 확인한다.
- 언어별 폰트 문자 범위, 줄높이, 글리프 누락을 확인한다. 서버 오류는 locale에 무관한 코드로 응답되고 앱의 선택 언어가 문구를 결정하는지 확인한다.

예상: 앱 언어 변경만으로 지원 화면 문자열이 갱신되고, 긴 문구는 줄바꿈/확장으로 완전히 읽힌다. 사용자 작성 방 문구는 그대로 보존된다.

### A3. 방 day/night 및 UI light/dark

- day, night, follow_time 방 설정과 system, light, dark UI 설정을 조합해 렌더한다.
- 네 조합(day+light, day+dark, night+light, night+dark) 각각에서 본문/작은 글자 4.5:1, 큰 글자 3:1 대비를 검사한다.
- 각 조합에서 장면 오브젝트, 마스코트, 텍스트, D-day, 입력 패널, 고정 버튼에 대한 보호 영역과 터치·접근성 가독성을 확인한다.
- 새 공간에서 생성자 IANA timezone으로 `follow_time`이 기본 선택되는지 확인한다. 설정에서 timezone/mode 변경 및 시간대 경계 동작을 확인한다.

예상: 네 조합 모두 보호 영역, 대비, 텍스트 가독성 규칙을 충족하고 방 모드 전환으로 인터페이스의 독립적인 light/dark 설정이 깨지지 않는다.

### A4. 마스코트 동작과 로더 (클라이언트)

- 전체 크기 방 화면에서 40초 주기로 인사 → 걷기 → 신나게 인사 → 올려다보기 → 엎드리기 → 잠자기 → 걸어 돌아와 인사를 반복하는지, 누르는 동안 신나게 인사 포즈가 나오는지 확인한다.
- 축소된 방(방 카드, 미리 보기 축소)과 미리 보기·적용 확인·되돌리기 확인 화면에서는 정지 포즈인지 확인한다.
- 동작 줄이기(iOS 동작 줄이기, Android 애니메이션 끔)를 켜면 마스코트는 서서 인사하는 정지 포즈, 로더는 첫 오브젝트 정지 그림, S04 편지는 정지인지 확인한다.
- 순환 로더(화분 → 풍선 → 창문 → 책, 4.8초; 창문은 로더 전용 그림이고 카탈로그에 없다)가 공간 만드는 중, 로그인 처리 중, 이동 중 등 모든 로딩 자리에서 같은 컴포넌트로 보이는지 확인한다.
- 마스코트 모션 중 방 오브젝트·보호 영역·고정 컨트롤을 가리거나 입력을 가로채지 않는지, 스크린 리더 낭독이 한 번만 되는지 확인한다.

예상: 움직임이 있어도 보호 영역과 접근성 트리는 달라지지 않고, 동작 줄이기에서는 모든 움직임이 멈춘다.

### A5. 홈 커버 사진

- 사진 없음 → 시스템 사진 선택기로 선택(사진 보관함 권한 요청 0회) → 자르기 → 올리는 중 → 표시, 바꾸기, 없애기 흐름을 확인한다. 상대 기기에서 앱을 열거나 동기화하면 같은 상태가 보이는지 확인한다.
- 허용 외 형식, 20MB 초과, 깨진 이미지, 이미지 헤더만 위장한 파일은 업로드가 거절되고 기존 사진이 유지되는지 확인한다.
- GPS 등 EXIF가 있는 사진을 올린 뒤 저장된 객체를 내려받아 메타데이터가 없는지 확인한다.
- 비구성원·종료 공간의 쓰기·읽기가 거절되고(RLS), 공개 URL이 존재하지 않으며, 서명된 URL이 만료 뒤 열리지 않는지 확인한다.
- 두 기기에서 거의 동시에 교체해도 사진 한 장만 남고(마지막 변경 우선) 먼저 올린 쪽 객체가 24시간 뒤 정리되는지, 두 기기 모두 마지막 변경자가 홈에 표시되는지 확인한다.
- 업로드 도중 네트워크 오류·앱 종료 후에도 기존 사진이 유지되는지, 오프라인에서 마지막 사진이 보이고 변경이 막히는지 확인한다.
- 매우 밝은 사진·매우 어두운 사진·흰색 단색 사진에서 홈 일수·날짜·상태 표시줄 글자가 4.5:1 이상인지(밝고 어두운 앱 모드 모두) 확인한다.
- 공간 종료 즉시 두 구성원 모두 사진을 읽을 수 없고(서명 주소 발급 `404`), 내부 보관 기간(서버 설정값) 경계에서 사진 객체가 삭제되는지(고정 시계로) 확인한다. 사진 URL·경로가 프롬프트·씬·AI 요청·로그에 없는지 provider spy로 확인한다.

예상: 사진은 두 구성원에게만 보이고 AI·장면으로 새지 않으며, 어떤 사진에서도 글자가 읽히고, 실패한 업로드가 기존 상태를 바꾸지 않는다. 사진에는 검수 단계와 신고 경로가 없고(신고·연결 끊기 대상 목록에 사진이 없는지 확인), 공간이 종료되면 즉시 읽을 수 없고 완전 삭제 때 파일이 지워진다.

### A6. 마일스톤 축하와 알림

- 방 시간대 기준으로 시작 날짜를 바꿔 50·100·200·300·500·1000일째(당일 = 1일째)와 주년(같은 달력 날짜: 1·2·3주년)을 각각 그 전날·당일·다음 날, 일곱째 날(보임)·여덟째 날(안 보임)로 만든다. 2월 29일 시작의 평년 주년이 2월 28일인지, 주년과 일수가 같은 날이면 하나만(주년 우선) 보이는지 확인한다. 기기 시계를 바꿔도 결과가 같다(서버 계산).
- 두 기기에서 같은 마일스톤: 한쪽이 카드를 닫아도 다른 쪽은 자기 첫 열기에서 한 번 본다. 같은 쪽은 다시 열어도 보이지 않는다. 방 말풍선을 닫아도 홈 카드가 사라진다(반대도 같다).
- 시작 날짜 수정: 이미 축하한 마일스톤은 날짜가 바뀌어도 다시 보이지 않는다. 바뀐 날짜의 마일스톤 날이 아직 오지 않았다면 기록이 지워지고 그날 다시 한 번 축하한다(`milestonesReset`, 알림도 다시 예약). 이미 지난 날짜로 바뀌면 기록이 없는 마일스톤만 7일 규칙을 따른다(주년 포함).
- 상대를 초대하는 중, 종료된 공간, 오프라인, 서버 오류: 앱 안 축하가 보이지 않고 나머지 기능이 그대로다. 오프라인에서 닫은 기록은 연결 후 한 번만 반영된다.
- **알림(옵트인)**: 앱 첫 실행에서 알림 권한을 묻지 않는다. 첫 축하 카드를 닫은 직후 사전 안내 시트가 한 번만 뜨고 "다음에"면 다시 뜨지 않는다(설정에서만). "알림 켜기" → OS 권한 허용: 설정 행이 켜짐, 다가오는 마일스톤 최대 3개가 오전 9시(방 시간대)로 예약됨(기기 저장소에서 확인, 서버에는 토큰·설정이 없다). 거절: 행이 "기기에서 알림이 꺼져 있어요" + 기기 설정 열기. 알림 끄기·로그아웃·공간 종료·연결 끊기(상대가 한 경우 종료 알림을 받는 때)는 예약이 모두 취소되고, 날짜 변경·시간대 변경·앱 업데이트는 재예약된다.
- 알림 문구에 이름·날짜·일수가 없는지(잠금 화면), 알림을 누르면 앱이 홈으로 열리고 축하 카드가 보이는지, 이미 본 마일스톤이면 카드 없이 홈만 열리는지, 같은 마일스톤이 두 번 예약되지 않는지 확인한다. 알림을 켜지 않은 기기에는 알림이 오지 않는다. 탭 바에 배지가 없다.
- 동작 줄이기: 마스코트와 반짝임이 정지하고 문구·버튼은 그대로다. ja/en/ko에서 카드 제목·본문·버튼이 잘리지 않고, 글자 130% 이상에서 카드가 세로로 쌓인다.
- 기념 제안: 입구 → 점유 시작 → 미리 보기(소품 5~6개 + 문구 1개) → 적용 확인("적용한 뒤에는 되돌릴 수 없어요") → 적용. 자동 적용이 없고, AI 요청 이력·일일 한도가 늘지 않으며, AI 동의 없는 구성원도 쓸 수 있다. 상대가 점유 중이면 시작되지 않고(`SESSION_OCCUPIED`), 자리가 모자라면 `placed < requested`와 안내, 자리가 없으면 `ROOM_FULL`. 기념 문구는 시작한 구성원의 앱 언어로 저장되고 문구 3개 한도를 지킨다.

### A7. 마스코트 되살림

- 프롬프트로 마스코트를 제거한 뒤: 방 화면에 고정 컨트롤 "모피 다시 부르기"가 보이고 누르면 기본 자리에 하나가 돌아온다(새 방 버전 `mascot_recall`, 16개 한도에 포함, 모습 불변). 상대가 점유 중이면 컨트롤이 비활성이고 이유가 보인다. 이미 있으면 아무 일도 없다(멱등). 한도가 가득이면 `ROOM_FULL`과 안내.
- 제거된 방을 다시 열면(점유자가 없을 때) 자동으로 한 번 되살아난다(가정). "모피를 다시 불러줘" 프롬프트도 같은 결과다. 프롬프트로 마스코트의 모습(옷·색·표정·교체)을 바꾸려는 시도는 어떤 경우에도 거절된다.

### B. AI 후보 / 동의 / quota

- 동의 없는 계정, 한 사람만 동의한 커플, 철회한 사용자, 종료 공간에서 요청한다.
- 정상, 부적절, 금지 IP 지칭, prompt injection, 잘못된 JSON, 폐기 ID, 보호 영역 충돌 응답을 mock한다.
- repair 1회 성공과 repair 후 실패를 각각 확인한다.
- **하루 3번째 성공한 미리 보기까지 허용, 4번째는 429**; 병렬 요청에서도 한도가 초과되지 않아야 한다. 방 시간대 자정 이후 초기화되고, 마일스톤 제안(AI 없음)은 계수하지 않는다. **거절(입력 정책)·검증 실패·2차 검사 실패·제공자 오류는 횟수를 쓰지 않는다**(가정); 이런 실패를 여러 번 만들어도 3번의 성공이 남아 있어야 한다.
- (한 공간만, FR-057) 이미 공간이 있는 사용자가 다른 공간의 유효한 초대 코드를 수락하면 `409 ALREADY_IN_SPACE`, 코드는 소모되지 않아 공간에서 나온 뒤 같은 코드로 가입된다. 이미 공간이 있는 사용자의 `POST /spaces`도 같은 오류다.
- (연령, FR-058) 가입 시작 화면의 약관 줄에 "만 14세 이상" 문구가 세 언어로 보이고 서버는 생년월일을 저장하지 않는다.
- (연결 끊기, FR-059) 확인 창이 "연결을 끊으면 {name}님은 이 공간의 방과 대화를 볼 수 없고, 이 공간이 종료돼요. 함께 쓰던 데이터는 삭제돼요."를 말하고(일수·복구 언급 없음), 확인하면 공간이 `ended`(`ended_reason=disconnect`)가 되며 두 사람의 읽기·쓰기가 즉시 막힌다. 상대 화면은 "{name}님이 연결을 끊었어요" 종료 알림을 보인다. 신고는 연결 끊기 없이 따로 접수된다.
- provider timeout/5xx 후 현재 테마와 사용자의 preview 상태가 안전하게 남는지 확인한다.

예상: 비동의 요청은 Anthropic provider spy 기준 네트워크 호출 0회, 검증 실패 결과 저장/공유 0회, 오류 로그에는 키/원문 없음.

### C. 두 멤버 권한·초대·실시간 sync

- A와 B는 같은 공간을 읽고, C는 공간 ID를 알아도 읽기/수정/채널 구독 불가.
- 24시간 만료·재사용·위조 초대 코드는 거절, 두 명을 채운 뒤 제3 멤버 수락 거절; 재발급 시 기존 미사용 코드를 무효화.
- A가 prompt-session을 점유 중이면 B는 공유 conversation/preview를 실시간 확인하지만 input, submit, apply는 사용할 수 없다. owner indicator와 composing/working 상태를 본다.
- A/B 동시 acquire 중 하나만 성공하고 다른 한 명은 `SESSION_OCCUPIED` 및 owner/expiry를 본다.
- A가 입력/생성하는 동안 heartbeat가 lease를 연장한다. A가 앱을 닫거나 3분 idle이 지나면 만료되고, B takeover 후 같은 대화와 preview를 이어서 본다.
- cancel, confirm에 성공하면 session이 해제되어 상대가 다음 acquire를 할 수 있다. 열린 대화 안의 undo는 session을 해제하지 않는다.
- 서버에서 session owner를 우회해 두 기기가 동시에 confirm/apply하도록 race를 발생시켜도 하나만 성공하고 version/idempotency guard가 중복 적용을 막는다.
- confirm 후 양쪽 화면이 동일한 version으로 sync된다. undo 후에는 양쪽이 같은 미리 보기를 본다.

예상: 어느 API 경로와 Realtime 채널에서도 제3자 공간 데이터가 노출되지 않는다.

### D. 미리보기·확정·세션 안 undo

- preview 직후 app 강제 종료/취소 후 current version이 바뀌지 않음.
- confirm 이후 버전 스냅샷이 하나 추가되며 두 구성원이 같은 결과를 봄.
- 세션 안 undo: 열린 대화의 마지막 미리 보기를 `reverted`로 바꾸고 바로 앞 미리 보기(없으면 현재 방 보기)를 두 구성원에게 보여 준다. 방 버전은 바뀌지 않고 점유는 유지된다. 되돌릴 후보가 없으면 `NOTHING_TO_UNDO`, 연속 undo는 이 대화의 미리 보기 범위에서 멈춘다.
- 적용한 뒤에는 undo를 호출해도 `ALREADY_APPLIED`로 거절되고 UI에도 되돌리기가 없다. 다시 적용(redo)은 존재하지 않는다.
- 적용 직전 확인 단계에 "적용한 뒤에는 되돌릴 수 없다"는 문구가 보이고, 확인해야만 confirm이 호출된다.
- Occupier만 preview를 적용할 수 있고, 성공한 confirm은 새 immutable snapshot 저장과 session release가 함께 처리됨.
- 두 simultaneous apply를 서버에 직접 보내면 stale/idempotent guard로 하나만 저장되며, 일반 UX는 active lease가 request를 serialize.

### E. 오프라인 / 공간 종료

- 온라인에서 동기화한 후 비행기 모드에서 D-day와 마지막 확정 방 표시.
- 오프라인 AI/초대/confirm/end 시 네트워크 요청을 큐에 보관해 나중에 자동 적용하지 않고 명확한 온라인 안내 제공.
- (종료 즉시 두 사람 모두 접근 상실, FR-023) 한 구성원이 `POST /end`(또는 `POST /block`)를 호출하면 같은 순간부터 **두 구성원의 클라이언트가 모두** 접근을 잃는다: 열려 있던 화면은 다음 호출·Realtime 끊김에서 종료 알림 화면(S14)으로 이동하고, 응답은 `{ "status": "ended" }`뿐이며 날짜·기간이 없다. 이미 종료된 공간(상대가 먼저 종료)에 다시 `end`를 호출하면 `404`다.
- (종료된 공간은 모든 클라이언트 호출에서 없는 공간, 가정) 종료 뒤 아래 호출이 모두 비구성원과 같은 `404`(또는 구독/서명 주소 거절)인지 확인한다: `GET /spaces/{id}/snapshot`, `prompt-conversation`, `prompt-session/acquire`, `decoration-previews`(생성·confirm·삭제), `generated-objects`(목록·상세·삭제), `home-cover`(GET·upload-url·PUT·DELETE)와 Storage 서명 주소, `milestones/current`·`seen`, `reports`·`reports/mine`, `room-mode`, `anniversary`, `block`, Realtime 채널 구독. RLS 직접 조회도 0행이다. 홈 커버 사진과 생성 장식이 즉시 읽히지 않는다.
- (종료 알림과 확인, FR-069) `GET /spaces/mine`이 `{ "active": null, "ended": { "kind", "by", "at" } }`를 돌려주고 `ended`에 공간 식별자·공간 데이터·삭제 일정 필드가 없다. 종료한 쪽은 `by: "me"`, 상대는 `by: "partner"`로 같은 종료의 알림을 각각 한 번씩 받는다. `POST /spaces/mine/ended/ack`는 204이고 멱등(두 번 호출해도 204)이며 이후 `ended: null`, 상대의 알림은 그대로다. 알림이 여럿이면 가장 최근 하나만 나온다.
- (새 공간 즉시, FR-057) 종료 직후 같은 사용자의 `POST /spaces` 201 또는 새 초대 수락 200이 기다림 없이 된다(`ALREADY_IN_SPACE` 아님). 새 공간이 활성인 동안에도 이전 공간은 어떤 경로로도 읽히지 않는다. 활성 공간이 이미 있는 사용자는 여전히 `409 ALREADY_IN_SPACE`다.
- (완전 삭제 작업, FR-024) 고정 시계로 `purge_after - 1초`에서는 아무것도 지워지지 않고, `purge_after`에서 `purge_expired_spaces()`가 공간의 **모든 행**(구성원·초대·방 테마와 버전·꾸밈 요청·프롬프트 세션/메시지·홈 커버 사진·마일스톤·생성 장식·생성 시도·신고·일일 요청 행·종료 알림)과 **Storage 객체**(홈 커버 현재 객체와 삭제 대기 목록)를 지운다. 생성 장식은 DB의 JSONB 행이라 행 삭제로 함께 사라지고 별도 Storage 객체가 없다는 것도 확인한다(나중에 장식용 Storage 객체를 도입하면 그 객체도 같은 작업의 파일 삭제 대상에 포함). 같은 작업을 다시 실행해도 오류 없이 변화가 없다(멱등). Storage 삭제를 일부러 실패시키면 공간은 `ended` 그대로(여전히 보이지 않음)이고 DB 행이 남으며, 다음 실행에서 정상 완료된다(부분 삭제 상태 없음). `generation_block` 지문은 남고 내용 없는 `deletion_started`/`deletion_completed` 이벤트만 남는다.
- (UI에 기간·복구 없음, FR-023) i18n 리소스(`ko`·`en`·`ja`)를 grep해 종료·연결 끊기 관련 문자열에 일수 숫자(예: `30`, `일`/`days`/`日` 단위의 기간 표현)와 복구 표현(`복구`·`restore`·`recover`·`復元`)이 없는지 확인한다(`room.recover.*` 같은 장면 다시 불러오기 키는 예외). 화면에 복구 버튼·종료일 안내가 없는지 S14, 설정, 연결 끊기 확인 창에서 수동으로 확인한다.
- (오프라인) 오프라인에서는 종료·연결 끊기 요청을 보내지 못하고 온라인 안내를 보인다. 종료 알림은 다음 온라인 호출에서 받는다.

### F. 생성 장식(US8, P2) — 모의 모델과 검증기로 먼저, 실제 모델은 게이트 G17

- (형식) `contracts/samples/generated-object/valid/*`는 검증을 통과하고 같은 입력은 같은 SVG 미리보기를 낸다. `invalid/*`는 각각 `_expectations.json`의 오류 코드로 거부된다(스크립트·URL·`data:`·참조·텍스트/이미지 도형·허용되지 않은 경로 명령·NaN/지수·범위 초과·팔레트 위반·도형 41개·12KB 초과·말풍선 영역/대비 위반·`__proto__` 등). 서버와 앱이 같은 샘플로 같은 결과를 낸다.
- (요청 순서) 모의 제공자로 정상 → 후보 `candidate` 생성·두 구성원 같은 미리 보기·점유자 확인 시 `active`와 방 반영·보관함 저장. 입력 정책 거절은 제공자 호출 0회, 검증 실패는 오류 피드백으로 1회 재시도 후 `GENERATION_FAILED`, 2차 검사 실패·호출 오류는 fail-closed.
- (횟수 의미) 성공 3회 뒤 4번째는 `429`; 거절·실패 10번을 만든 뒤에도 성공 3회가 남음; 시도 30회·분당 4회·연속 거절 쿨다운이 `RATE_LIMITED`; 같은 멱등 키 재요청은 한 번만 생성·한 번만 계수.
- (레드팀) `ai-guardrails.md` 부록 A 44개를 분류 스텁·결정론 필터에 돌려 거절 대상 100% 거절, 허용 대상 ≥90% 허용(SC-008, 모의). 혼합 요청은 전체 거절. 마스코트·캐릭터 요청은 `off_purpose`, 작은 방 소품은 허용(마스코트·앱 캐릭터를 닮은 소품·글자·로고·브랜드 소품은 거절).
- (보관함) 상한(`generation_library_cap`, 기본 40; 설정값을 올리면 바로 풀림)에서 `LIBRARY_FULL`(모델 호출 0회), 방에 놓인 장식도 삭제할 수 있고 삭제하면 방에서도 사라지며(방 버전 불변, 읽을 때 걸러냄, 다음 후보 장면은 삭제된 참조를 뺌), 후보는 24시간 뒤 정리, 공간이 종료되면 즉시 읽을 수 없고 완전 삭제 때 함께 삭제.
- (RLS) 다른 커플·비구성원·종료 공간에서 `generated_object`·`generation_attempt`·`report` 읽기/쓰기/구독이 모두 거부되고, 클라이언트 직접 insert/update/delete는 거부된다. 커플 A의 장식 ID로 커플 B의 장면에 참조를 넣으면 검증에서 거부된다.
- (킬 스위치) `generation_enabled=false`: 새 요청 `GENERATION_DISABLED`, 기존 장식과 카탈로그 꾸미기는 계속. `generated_render_enabled=false`: 방·보관함에서 생성 장식이 그려지지 않음. 검증기 버전 상향: 렌더 전 재검증 실패 장식은 그려지지 않음.
- (렌더) 같은 문서가 iOS·Android에서 같은 모양으로 그려지고(스냅샷), 말풍선 글자 대비 4.5:1 이상, 배경 조각이 마스코트·카탈로그 오브젝트·텍스트 아래이며, 보호 영역과 D-day·고정 컨트롤을 가로채지 않는다(배경 띠 아래의 대비 포함). 동작 줄이기·큰 글자·고대비에서 읽힌다.
- (개인정보) 동의 전·철회 후 입력 정책·생성·2차 검사 호출 모두 0회, 로그에 프롬프트·키·서명 URL 없음, `generation_attempt` 프롬프트가 30일 뒤 삭제.

### G. 신고(US9, P2)

- 장식 상세 시트에서 신고(사유 4가지 + 선택 메모) → 접수 201 → 신고자 읽기에서 장식 즉시 숨김, 상대 화면은 그대로 → 운영자 `review_report(removed)`: 두 사람 화면에서 제거(방 버전은 그대로, 읽을 때 걸러냄), 같은 프롬프트 지문의 재생성 거절, 두 구성원이 "검토 결과 이 장식은 방에서 빠졌어요"를 한 번씩, 신고자 상태 "검토를 마쳤어요". `kept`는 신고자에게만 안내되고 숨김 유지.
- 신고 내용·메모·누가 신고했는지가 상대에게 노출되지 않음(`GET /reports/mine`은 본인 것만), 하루 10건 초과는 `429 REPORT_RATE_LIMITED`, 같은 장식 중복 신고는 멱등, 다른 공간의 장식 ID는 404, 방 전체 신고는 `room_scene`으로 접수, 연결 끊기와 별개(신고만으로 공간이 종료되지 않음), 홈 커버 사진은 대상이 아님.

### H. 계정 삭제(US10, P1, 출시 필수 · 모의 공급자와 고정 시계로, 실제 공급자 호출은 출시 게이트 G18에서 수동 확인)

- (경로·확인) 설정 > 위험 구역에 "계정 삭제"(`set.account.delete`)가 눈에 띄게 있고, 누르면 결과 설명(`acct.delete.*`)이 나온다. "내용을 확인했어요"(`end.check`)를 켜기 전에는 진행 버튼이 비활성이다. 확인 단어 입력은 없다. 재인증 시트는 카카오·Apple·이메일 코드이고 성공한 뒤에만 빨간 "계정 삭제하기"가 활성이다. `DELETE /account`에 재인증이 없거나 5분이 지났으면 `401 REAUTH_REQUIRED`이고 아무것도 바뀌지 않는다(공급자 불일치·Apple 코드 교환 실패도 같다).
- (공간 상태별) ① **활성 공간 + 상대 있음**: 같은 트랜잭션에서 공간 `ended`(`ended_reason = account_deletion`, `ended_by_user_id`), 두 구성원 `space_active = false`, 상대의 `space_end_notice(kind = account_deleted)`, 삭제한 사람에게는 알림 행 없음, 상대의 모든 공간 호출 `404`(E의 종료 접근 차단 목록과 같음), `purge_after` +30일. ② **공간 없음**: 계정만 삭제. ③ **혼자인 공간(상대 없음)**: 공간 `ended`, 알림 행 0개. ④ **대기 중인 초대 코드**: `revoked`(그 코드로 수락하면 실패). ⑤ **점유·열린 프롬프트 세션·진행 중 생성 요청**: 점유 `released`(`release_reason = account_deletion`), 열린 세션 닫힘, `queued` 요청 `cancelled`, 상대는 종료 알림만 본다.
- (상대 화면) 상대가 앱을 열면 S14에 "상대가 계정을 삭제했어요"(`end.byPartnerDeleted`, 이름 없음)와 "함께 쓰던 데이터는 삭제돼요. 새 공간을 시작할 수 있어요."가 **한 번** 보이고 `POST /spaces/mine/ended/ack`(204, 멱등) 뒤 사라지며 공간 만들기·코드 입력으로 간다. `GET /spaces/mine`의 `ended`는 `{ "kind": "account_deleted", "by": "partner", "at" }`뿐이고 삭제한 사람의 이름·식별자·공간 식별자·삭제 일정 필드가 없다. 서버 푸시가 없음을 확인한다(앱을 열어야 보임). 상대는 확인 직후 새 공간을 만들 수 있다(`ALREADY_IN_SPACE` 아님).
- (모든 기기 로그아웃) 두 기기에 로그인한 사용자가 한 기기에서 삭제하면 다른 기기의 다음 호출이 `401`이고 로그인 화면으로 간다. 리프레시 토큰으로 새 액세스 토큰을 받는 시도도 실패한다. **만료 전 JWT를 미리 캡처해 접수 뒤에 보내면** 읽기·변경 모두 거절된다(읽기 `401`, 변경 `401` 또는 `409 ACCOUNT_DELETING`) — 서버가 요청마다 `user_profile.status`를 확인하는지 직접 확인한다. Realtime 구독이 끊긴다. 삭제한 기기는 `202` 직후 로컬 로그아웃·예약 알림 전체 취소·로컬 캐시(공간·사진·장식·임시 파일) 삭제를 한다. 다른 기기에 남은 로컬 예약 알림은 그 기기가 다음에 앱을 열어 로그아웃임을 알 때 취소된다(서버가 못 지움: 알려진 한계로 기록).
- (공급자 해제, 모의) **Apple**: 재인증 때 받은 `authorizationCode`를 서버가 토큰으로 바꾸고 revoke를 부른다 — 코드 교환 실패는 접수 전에 `401 REAUTH_REQUIRED`; revoke 성공 전에는 `provider_revoked`로 가지 않는다; 이미 해제된 경우의 오류는 성공으로 본다; 첫 시도 실패 시 토큰은 암호화되어 최대 24시간만 남고 성공 또는 시간 초과 때 null이 된다. **Kakao**: 서버 비밀 키로 unlink를 부르고 성공 응답을 받은 뒤에만 `provider_revoked`로 간다; 대상 ID를 인증 사용자 identity에서 읽는다(재시도 때도). **이메일**: 이 단계를 건너뛴다. 키·토큰·인증 코드가 로그·오류·API 응답에 없다.
- (실패 주입·재개) 각 상태 경계에서 서버를 죽이거나 실패시킨다: `begin_account_deletion` 트랜잭션 중간 실패(전체 롤백, `202` 없음, 모든 것이 그대로) / `space_ended` 뒤 공급자 실패(백오프 재시도, 사용자는 이미 로그아웃, 정상화 후 이어서 진행) / `provider_revoked` 뒤 `deleteUser` 실패 / `auth_deleted` 뒤 껍데기 전환 전 재시작 → `lifecycle-sweep`이 `state`에서 이어서 `done`까지 끝낸다. 같은 `DELETE /account`를 반복(멱등, `202`)해도 한 번만 처리된다. 지속 실패는 내용 없는 운영 경고만 남긴다. `done`에 이르지 못한 채 멈춘 계정이 0개인지(SC-011) 확인한다.
- (Storage 소유자) 홈 커버 업로드(업로드 주소 사용)와 교체·삭제 뒤에 `storage.objects`의 모든 객체에서 소유자가 사용자가 아닌지 확인하고, 사진이 있는 사용자의 `deleteUser`가 Storage 소유 때문에 막히지 않는지 확인한다.
- (껍데기 프로필) 계정 삭제 뒤 `user_profile`이 `shell`이고 개인 필드가 모두 null이며(`locale`·`time_zone`·`ui_theme`), 종료된 공간의 `space_member`가 껍데기를 가리키는 동안은 FK 위반 없이 유지된다. AI 동의 열이 모든 구성원 행에서 비워졌다. `purge_after`에서 `purge_expired_spaces()`가 공간 행과 함께 참조 없는 껍데기와 `account_deletion` 행을 지우고, 다른 종료된 공간이 아직 가리키는 껍데기는 남기며(여러 공간), 공간이 없던 사용자는 `finish_account_deletion` 때 프로필 행이 바로 사라진다. `auth.users`에 대한 FK가 없음을 스키마 검사로 확인한다.
- (재가입) 같은 이메일·카카오·Apple 계정으로 바로 다시 가입하면 **새 `user_id`의 빈 계정**이다: 이전 공간·데이터·동의 기록·로그인 연결이 없고, 새 공간을 만들 수 있다(차단 기간 없음, 열린 질문).
- (경합) 계정 삭제와 `purge_expired_spaces()`가 같은 공간에서 동시에 돌아도 공간 행 잠금 하나로 직렬화되어 한 번만 처리되고, 이미 `ended`·퍼지된 공간의 `end_space`는 오류 없이 아무 일도 하지 않는다. 상대가 같은 순간 `POST /end`·`POST /block`을 누르면 공간은 한 번만 종료되고 상대(또는 나)의 알림 이유는 먼저 성공한 쪽(`ended`/`disconnect`/`account_deleted`)을 따른다. 상대가 먼저 종료한 공간에서 삭제하면 계정 삭제는 정상 진행되고 공간은 그대로다.
- (오프라인·실패 UI) 오프라인에서는 "인터넷에 연결되어야 계정을 삭제할 수 있어요"(`acct.delete.offline`)만 보이고 요청이 나가지 않으며 큐에 쌓이지 않는다. 접수 전 서버 오류는 `acct.delete.fail.*`("아직 아무것도 지워지지 않았어요")이고 다시 시도할 수 있다. 본인 확인 실패는 `acct.delete.reauth.fail`.
- (문구 검사) i18n 리소스(`ko`·`en`·`ja`)의 `acct.*`·`set.account.*`·`end.byPartnerDeleted`에 일수 숫자, 복구·유예(`복구`·`restore`·`recover`·`grace`·`30일`·`復元`) 표현이 없는지 grep한다. 상대 안내에 이름이 들어가지 않는지(S14 `account_deleted`) 확인한다.
- (스토어·웹 점검) 설정 > 계정 삭제가 앱 안에서 몇 번 눌러 닿는지, `docs/account-deletion-web.md` 페이지 본문이 삭제되는 것·내부에 남는 것·앱을 못 여는 경우의 요청 방법을 3개 언어로 담는지, 페이지 URL이 Google 데이터 보안 양식과 앱 정보에 맞는지, Apple 심사 노트(경로·재로그인·토큰 해제)가 있는지 출시 전에 확인한다(G18).

예상: 접수된 순간부터 그 사용자의 모든 호출이 실패하고, 상대 공간은 즉시 읽을 수 없으며, 공급자 연결이 끊기고 개인 필드가 사라지고, 같은 로그인은 빈 계정이 되며, 어떤 실패·재시작에서도 삭제가 일부만 된 채 멈춘 계정이 남지 않는다.

## 기기 및 스토어 점검

- 사진 선택기(iOS PHPicker, Android Photo Picker)가 권한 팝업 없이 동작하는지, HEIC가 변환되어 올라가는지 확인.
- SDK/Skia 지원 조합의 iOS와 Android 개발/릴리스 빌드, 스크린 리더, dynamic type, 화면 회전/안전 영역을 실제 기기에서 확인.
- scene canvas의 장식은 hit target을 가로채지 않고, D-day·모든 고정 컨트롤은 네이티브 접근성 트리에 남는다.
- EAS 내부 빌드/TestFlight/Play internal test에서 Kakao·Apple·이메일 redirect를 확인.
- 심사 계정은 반복 사용할 수 있는 고정 샘플 장면과 신고/연결 끊기 경로를 포함하고, 심사 노트에 고정 렌더러가 데이터만 처리한다고 설명.
- 개인정보·AI 해외 처리·UGC/신고 연락처·연령 등급/미성년자 정책을 앱 심사 제출 직전 다시 확인.
- **계정 삭제 출시 전(G18)**: 심사 노트에 경로(설정 > 계정 삭제), 재로그인 확인, Sign in with Apple 토큰 해제, 공유 공간 콘텐츠 처리와 내부 보관 안내를 쓰고, Google 데이터 보안 양식의 삭제 항목과 앱 밖 삭제 링크(소유자가 만든 `mopiru.jinjinstar.com/delete-account`)를 입력하며, 카카오 연결 끊기 사용 권한·서버 비밀 키, 개인정보 처리방침(즉시 삭제·익명화되는 항목 vs 최대 30일 내부 보관)을 법률 검토 뒤 최종 확인한다. 앱 밖 삭제 요청(가입 이메일 회신 본인 확인, 가정)의 운영 절차를 시험한다.
- **생성 장식 출시 전**: Apple 1.2(신고 수단·필터·차단·연락처)와 Google Play AI 생성 콘텐츠(앱 안 신고·플래그)·UGC 정책, Anthropic 사용 정책(2026-11-12 시행 개정판), 약관·개인정보 처리방침 변경, 연령 등급 설문 갱신, "연결 끊기"가 차단으로 인정되는지를 현재 공식 문서로 확인(`research.md` 9장의 미확인 항목). 심사 노트에 생성 장식이 데이터(JSON)이고 고정 렌더러가 그린다는 점, 신고·운영 제거 경로, 킬 스위치를 설명.

## 성공 판정

SC-001~005와 SC-008(실제 모델)·SC-010·SC-011(H 시나리오의 모의·고정 시계 테스트)은 별도 계측/제품 검증으로 측정한다(SC-001~003은 PoC 동안 측정하지 않는다, `spec.md` Decided 26). 저장소 검사 통과만으로 사용자 성공 기준이 입증되었다고 표시하지 않는다. 미리보기에서 확인되지 않은 변경이 반영되는 경로는 0건이어야 한다.
