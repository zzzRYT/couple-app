# 구현 계획: 프롬프트로 꾸미는 커플 D-day와 우리 방

**작업 브랜치**: `fm/cpl-plan` | **작성일**: 2026-10-24 | **명세**: [spec.md](./spec.md)

**입력**: `specs/001-couple-prompt-todo/spec.md` 및 제공된 제품·시각·장면 배치 조사 보고서

## 요약

Expo / React Native 모바일 앱에 메인 D-day 화면과 둘만의 자유 배치 방을 제공한다. 장식 2D 오브젝트와 짧은 문구만 2D 장면 그래프에 저장하고, D-day 의미 위젯과 조작 컨트롤은 장면 캔버스 밖의 네이티브 뷰로 렌더링한다. 서버 함수가 동의와 공간 권한을 확인한 뒤 Claude 구조화 출력을 검증해 미리보기 후보를 만들며, 사용자가 확인한 불변 버전만 공유 방에 반영한다. Supabase(Postgres, Auth, Realtime, Edge Functions)를 권장안으로 제안한다.

## 고정 결정

- 앱은 모바일 전용이며 Expo / React Native로 만든다. 작성일의 최신 안정 기준은 Expo SDK 58(2026-10-15), React Native 0.88(2026-10-19), React Native Skia 3.7.4(2026-10-23)이다. Skia는 장식 씬 렌더링에만 사용하고, Expo SDK 58에서의 네이티브 호환성을 구현 시작 시 다시 확인한다.
- 방은 보호 영역을 적용한 자유 배치 2D 장면 그래프다. 장면 그래프에는 라이선스가 확인된 카탈로그 오브젝트와 짧은 텍스트만 둔다.
- D-day 의미 위젯과 고정 컨트롤은 장면 캔버스 밖의 네이티브 뷰로 그린다. D-day 위젯은 별도 표현 데이터로 이동·크기·스타일을 바꾸거나 방에서 숨길 수 있지만, 날짜·정확성·접근성은 앱이 소유한다.
- V1은 사진 같은 래스터 생성 이미지, 임의 SVG 문자열, 외부 코드를 제공하지 않고, 사용자 사진 업로드는 **커플당 홈 커버(배경) 사진 한 장**만 예외로 허용한다. 갤러리·타임라인·방 장면·프롬프트에 쓰는 사진은 제외한다. 홈 커버 사진은 장면 데이터와 분리되어 AI에도 보내지 않는다(아래 "홈 커버 사진"). 장면 데이터는 고정 앱의 렌더러가 읽는 값이며 코드·스크립트·액션·URL을 포함하지 않는다. **예외(P2, 2026-10-27 가정)**: 프롬프트로 만든 제한된 벡터 장식(배경 조각·말풍선 틀)은 허용목록 JSON 도형 목록으로만 저장·렌더하고 SVG 문자열은 받지 않는다(아래 "생성 오브젝트").
- AI 호출은 서버 함수에서만 한다. API 키는 서버 비밀 저장소와 개발자의 비밀 환경에만 두며 저장소, 로그, 앱 번들, PR 문구, 채팅에 넣지 않는다. 개발·PoC 중에는 소유자의 **Claude Max 요금제에 포함된 월 $100 API 크레딧**(요금제에 Console 조직 하나를 연결해 받음)로 충당하고, Console **API 키**를 **서버의 비밀 키**(Supabase Edge Function secret)로만 둔다. 소유자의 채팅 로그인·Claude Code 구독 한도·OAuth 토큰은 앱이나 서버에 쓰지 않는다(Console API 키만). 이 프로젝트 전용 Console workspace에 지출 한도를 둔다. 크레딧은 결제 주기마다 지급되고 남은 것은 주기 끝에 소멸하며(이월 없음), 잔액이 0이면 다음 지급 때까지 API 요청이 멈춘다(요금제에 청구되지 않음). 조직 연결은 소유자가 직접 바꿀 수 없으니 프로젝트가 쓸 조직을 연결한다.
- AI 처리 전에 해외 처리·전송 데이터·목적을 안내하고 명시적 동의를 받는다. 동의 전·철회 후에는 전송하지 않는다. 프롬프트에는 장면을 꾸미는 데 필요한 최소 데이터만 포함한다.
- 커플당 하루 **3회**는 남용 방지 상한이다(처음 제안은 10회, 이후 5회였다). **성공한 미리 보기만** 센다(거절·실패는 세지 않고 별도의 시도 한도가 남용을 막는다, 가정). 방의 시간대 자정에 초기화한다. 결제·가격 상품과 연결하지 않는다.
- OAuth 로그인(우선 Sign in with Apple만, 카카오는 비활성 플래그, 2026-10-27 소유자 결정)을 지원하고, 만료되는 공유 초대 코드로 두 번째 구성원을 초대한다.
- 어느 구성원이든 공간을 종료할 수 있다. 종료는 **소프트 삭제**다: `couple_space.status`가 `active | ended`로 바뀌고 두 구성원의 접근이 같은 트랜잭션에서 끊긴다. **이용자용 복구 기능은 없다.** 서버는 내부적으로 `purge_after`(종료 + 30일, 서버 설정값)까지 두었다가 예약 작업으로 완전히 삭제한다. 앱은 이 기간이나 복구 가능성을 어디에도 알리지 않는다. "한 공간만"은 활성 공간만 세므로 종료 직후 새 공간을 시작할 수 있다(`spec.md` Decided 33~35, 가정; 이전 Decided 23·24는 대체됨).
- UI에는 AI 배지를 넣지 않는다. 내부 이력에 생성 출처를 기록한다. 법률상 고지·표시 의무는 출시 전 검토한다.
- 캘린더, 할 일, 홈 커버 사진 한 장을 제외한 사진 업로드는 제외한다.
- Backend는 Supabase Postgres/Auth/Realtime/Edge Functions로 결정한다. 프로젝트 DB는 Supabase Northeast Asia (Seoul, `ap-northeast-2`)를 권장 기본 region으로 사용한다.
- AI 모델 정책은 Haiku 5.5 기본, 품질 실패 사례에 제한적으로 Sonnet 5.5 승급이며 개발에는 제공된 Anthropic credit을 사용한다.
- 초대 코드는 8자(4-4, 혼동 문자 0/O·1/I 제외)이고 24시간 후 만료하며 한 번만 수락 가능하다. 재발급은 이전 미사용 코드를 무효화한다.
- 한 사용자는 한 번에 **하나의 공간**에만 속한다(FR-057). 이미 공간이 있는 사용자의 초대 수락·새 공간 생성은 서버가 거절하고 초대 코드는 소모하지 않는다.
- 최소 연령은 **만 14세**다(FR-058). 가입 시작 화면 문구로 확인하고 생년월일은 받지 않는다(가정). 문구는 법률 검토 전이다.
- ~~이메일 로그인은 6자리 코드가 기본이고 메일의 링크도 허용한다.~~ 2026-10-27: 이메일은 제품 로그인에서 제거하고 개발 빌드(`APP_VARIANT=development` + `EXPO_PUBLIC_DEV_EMAIL_LOGIN=true`)와 로컬 스택에서만 테스트 로그인으로 쓴다(가정). iOS는 `expo-apple-authentication` 네이티브 시트 + Supabase `signInWithIdToken`(해시 nonce), Android는 Apple 버튼 없음(웹 OAuth 대체는 Services ID·서명 비밀이 필요해 보류).
- 신고와 **연결 끊기**(예전 이름 "차단")는 별개 기능이다. 연결 끊기는 상대의 접근을 즉시 끊고 공간을 종료한다(소프트 삭제, `ended_reason = disconnect`, 복구 없음, FR-059). API·데이터 이름은 `block`을 유지한다.
- **계정 삭제는 첫 버전(P1, 출시 필수)에 있다**(2026-10-27 7차 답변, `spec.md` Decided 41~46, 모두 가정): 설정 > 위험 구역 > "계정 삭제", 결과 설명 + 체크 + 재인증 + 빨간 버튼, 유예·복구 없음. 접수되면 모든 기기에서 즉시 로그아웃, 개인 데이터 즉시 삭제·익명화, 활성 공간은 공간 종료와 같은 소프트 삭제(`ended_reason = account_deletion`)로 끝나고 상대에게는 이름 없이 "상대가 계정을 삭제했어요". 서버는 멱등 상태 기계(`account_deletion.state`)로 Apple revoke·카카오 unlink → Supabase 인증 사용자 삭제를 실행한다. MVP 컷에는 없지만 **없으면 스토어 심사·공개 출시가 막힌다**(게이트 G18). 아래 "계정 삭제 (P1, 출시 필수)".
- **개발 환경 비용은 무료로 시작한다**: Supabase 무료 플랜(서울 리전; 무료 프로젝트는 비활동 시 일시 정지되므로 배포 전에 확인), Expo 무료 계정, 개발 AI는 Max 요금제 포함 월 $100 API 크레딧(개념 증명 규모, 테스트 사용자 몇 명; 소유자는 포함 크레딧이 상업 서비스용이 아니라고 이해하고 있고 이는 Anthropic 공개 페이지로 확인되지 않았다). 운영 요금제·지출 상한·AI 승급 기준과 공개 출시 전 유료 크레딧 전환·상업 약관 확인은 출시 전에 정한다. 개발자 계정은 개인 계정으로 시작한다(Apple, Google Play, Supabase).
- 한 커플 공간에 prompt session owner는 한 명만 둔다. 두 구성원은 shared conversation/preview를 실시간 확인하며, 비점유자는 읽기 전용이고 점유자만 입력·요청·적용한다. idle lease는 3분(만료 30초 전 경고)으로 결정했고 서버 설정값이다.
- 출시 언어는 한국어(`ko-KR`), 영어(`en-US` 기본 locale variant 제안), 일본어(`ja-JP`) 세 가지다. 모든 UI 문구는 번역 리소스 기반이며, locale은 기기 언어 기본값과 앱 내 재정의를 지원한다.
- 앱의 독창적인 마스코트는 앱 소유 고정 캐릭터이며 새 방의 기본 오브젝트다(메인 페이지에는 표시하지 않고 온보딩 히어로 한 곳에만 쓴다). 이용자는 마스코트를 꾸미거나 변형할 수 없다(착용 슬롯·팔레트·표정 선택·생성 변형 없음, 첫 버전 범위 밖). 포즈와 움직임은 앱이 정한 고정 동작이다.
- 방 테마는 낮/밤 variant를 모두 저장한다. `follow_time`을 기본으로 하고 커플 공간 생성자의 IANA 시간대를 사용하며 설정에서 모드나 시간대를 바꾼다. UI 다크 모드는 별도 기기별 설정이며 `system` 기본값에 수동 light/dark override를 제공한다.

## 기술 맥락

**언어/버전**: TypeScript, Expo SDK 58 (2026-10-15), React Native 0.88 (2026-10-19; SDK 58 지원), React Native Skia 3.7.4 (2026-10-23). 출시 시점에 SDK/Skia 호환 행렬을 다시 고정한다.

**주요 의존성**: Expo Router, Expo Localization (`expo-localization`), `i18next` + `react-i18next` 제안, `@shopify/react-native-skia`, Supabase React Native 클라이언트, 서버 Edge Functions, Claude Messages API 구조화 출력.

### 다국어 구조 제안

- 화면 컴포넌트에는 표시 문자열을 직접 쓰지 않고 네임스페이스별 번역 키를 호출한다. 키는 `area.component.state` 형태(예: `room.prompt.submit`)로 관리하고 interpolation 변수와 plural 규칙을 번역 리소스에 정의한다.
- `expo-localization`으로 선호 locale을 읽고, `i18next`와 `react-i18next`로 한국어(`ko-KR`), 영어(`en-US`), 일본어(`ja-JP`) 리소스를 연결한다. 앱 내 선택은 기기 언어보다 우선한다. `Intl.DateTimeFormat` / `Intl.NumberFormat`으로 현지 날짜·숫자 형식을 쓰며 D-day 어휘와 일본어 연월일 순서/plural는 locale별 메시지 리소스로 관리한다.
- 언어 추가 절차: key manifest 갱신 → 번역 → 누락/미사용 키 및 interpolation 확인 → 폰트 glyph/license 확인 → pseudo-localization과 실제 번역으로 text expansion 측정 → 기기 언어/앱 내 언어 전환, layout 및 날짜/숫자 규칙 검수. 출시 지원 set은 ko-KR/en-US/ja-JP다.
- AI 프롬프트는 지원 언어 어느 것으로나 허용한다. AI는 요청 언어를 유지하며 커플이 쓴 방 문구는 입력 원문 그대로 저장한다. 서버 오류는 `VERSION_CONFLICT` 같은 언어 중립 코드만 반환하고 UI가 현재 locale 리소스에서 메시지를 선택한다.
- 권장 번들 font families: Inter (Latin/Latin-ext), Noto Sans KR (한글), Noto Sans JP (일본어). 언어 간 CJK glyph coverage를 추정하지 말고 각 locale의 한글/Latin/Japanese glyph fixture를 검증한다. Google Fonts metadata와 Noto 공식 repo는 family들을 SIL Open Font License로 표기한다. Noto Sans KR subset variable TTF는 약 9.93 MB, Noto Sans JP subset variable TTF는 약 9.15 MB이며 합계 약 19.1 MB로 Inter 파일과 앱 압축 전 크기는 별도다. 라이선스와 reserved name 고지를 번들에 포함하고, 실제 iOS/Android EAS artifact 크기를 측정해 필요한 weight/file subset만 확정한다. 크기 및 라이선스 근거는 [research.md](./research.md)의 공식 출처(접근 2026-10-24)를 따른다.
- 소스 확인일(2026-10-24): Expo 공식 [Localization 가이드](https://docs.expo.dev/guides/localization/)는 `expo-localization`, 앱 언어 선택, `Intl` 포맷을 안내하고 [expo-localization API](https://docs.expo.dev/versions/latest/sdk/localization/)에서 locale 정보를 제공한다. Expo 예시의 `i18n-js` 대신 키 기반 namespace와 React 통합을 위해 공식 [i18next 시작 문서](https://www.i18next.com/overview/getting-started) 및 [react-i18next 시작 문서](https://react.i18next.com/guides/quick-start)를 적용 후보로 제안한다.

### 마스코트와 방 테마

- 고정된 `app_mascot` 카탈로그 오브젝트는 앱 소유의 고정 캐릭터다(원본은 소유자가 생성형 AI 도구로 만든 마스터를 그대로 사용하기로 했고 약한 저작권 보호 위험을 수용했다. 닮음 검사·법률 검토는 출시 전 권장). 새 커플 방에 기본 1개 배치한다. 이용자 설정 상태(착용·색·표정·포즈 선택)는 저장하지 않으며 포즈는 앱이 정한다. 위치와 크기는 프롬프트로 정할 수 있고 방에서 제거할 수도 있지만(결정), 방에는 항상 하나가 있어야 하므로 되살림 규칙을 둔다(방을 다시 열 때 점유자가 없으면 클라이언트가 `mascot-recall`을 자동 호출 + 고정 컨트롤 "아루미 다시 부르기", 시점은 가정). 프롬프트로 모습을 바꿀 수 없다.
- 24–36개 자산 범위는 방 안 마스코트 포즈와 일반 방 오브젝트를 포함한다. 디자인이 실제로 내놓은 구성은 방 안 마스코트 포즈 6 + 일반 오브젝트 18 = 24다. 소품 포즈 일러스트 5종은 방 밖용이고 카탈로그에 세지 않는다. 마스코트는 씬 최대 16개 제한에 포함된다.
- **마스코트 동작(클라이언트 전용)**: 전체 크기 방 화면에서 포즈 이미지 6장을 40초 주기로 번갈아 보여 주며 걷는 구간에서는 좌우 반전과 위아래 흔들림을 쓴다. 누르는 동안 신나게 인사 포즈, 동작 줄이기에서는 서서 인사 포즈 한 장이다. 축소된 방 보기(방 카드·미리 보기)는 정지 포즈다. 이 동작은 장면 문서·서버 상태·AI 출력과 무관하게 앱이 정한 고정 동작이다(디자인 `interaction-notes.md` §11). 구현은 Skia/네이티브 애니메이션 중 성능 검토 후 고른다.
- **로딩 표시**: 화분 → 풍선 → 창문 → 책 순환 로더(4.8초)를 공용 컴포넌트로 만들어 전역 기본 로딩 표시로 쓴다. 창문은 **로더 전용 그림**이고 카탈로그에 넣지 않는다(카탈로그 24개 그대로, `spec.md` Decided 25, 가정). 동작 줄이기에서는 정지 그림이다(`components.md`).
- `RoomThemeDocument`는 `day`와 `night`의 배경/팔레트 토큰 및 catalog asset variant, mode와 IANA timezone을 보유한다. 기본 mode는 `follow_time`, timezone은 공간 생성자의 것으로 초기화하고 설정에서 변경한다. 기기별 UI 모드는 `system | light | dark`, 기본 `system`이다.
- validator는 마스코트 기본 자산의 단일성을 검증하고 마스코트 교체·변형·상태 필드를 거부한다. 보호 영역, 대비, 글자 가독성은 day/night 방 변형과 light/dark UI의 네 조합에서 확인한다.

### 공유 프롬프트 세션

- 공간당 하나의 DB lease만 `occupied`일 수 있다. `PromptSession`에는 session ID, owner member, last activity, heartbeat 및 expiry를 둔다. idle timeout은 3분(만료 30초 전 경고)으로 결정했고 서버 설정값이다.
- prompt, status, preview는 shared conversation에 저장한다. Supabase Realtime은 두 구성원에게 message/preview ID, owner ID와 expiry만 알리고, 각 구성원은 RLS가 적용된 conversation endpoint에서 같은 대화와 preview를 불러온다.
- 점유자는 입력·제출·적용·취소·**세션 안 되돌리기**를 사용할 수 있다. 상대 화면은 live read-only로 대화와 preview를 보여 주고 owner/presence 및 expiry를 표시한다. 취소와 성공한 confirm은 DB transaction에서 저장/상태 전환과 함께 lease를 해제한다. 세션 안 되돌리기는 열린 대화의 마지막 후보를 `reverted`로 바꾸고 바로 앞 후보(없으면 현재 방 보기)를 다시 보여 줄 뿐이며 lease를 풀지 않고 방 버전도 바꾸지 않는다. **적용한 변경은 되돌릴 수 없고 다시 적용(redo)도 없다.** 앱은 적용 확인 단계에서 이를 알린다.
- heartbeat는 사용자 입력/모델 생성이 진행 중일 때 server clock 기준으로 연장한다. 앱이 background/닫힘 상태이거나 idle limit에 도달하면 만료된다. 다른 멤버의 takeover는 `expectedOwnerUserId`와 만료 시각을 비교해 원자적으로 owner를 갱신하며 shared preview를 이어서 볼 수 있다.
- confirm은 `session owner + expected version + idempotency key`를 서버 transaction에서 함께 검사한다. occupancy가 정상 입력을 직렬화하며 version guard는 두 기기의 동시 apply/늦은 retry로 인한 이중 적용을 막는 최종 보호다.
- **서버에 계속 저장하는 것(되돌리기·기록을 뺀 뒤에도)**: 적용된 버전 스냅샷(AI 출처·작성자·시각의 감사 기록, 적용 후 되돌리기나 열람은 없음), 요청 이력(하루 3회 한도·남용 조사), AI 처리 동의 기록, 종료된 공간의 내부 보관 데이터(`purge_after`까지). 이용자 화면 기능이 아니라 안전·남용 방지·동의·삭제 처리를 위한 저장이다.
- 데이터 기본 보관값: cancel/expire된 미적용 preview는 그 시각부터 24시간 보관 후 삭제, 적용된 prompt/message 원문은 30일 보관 후 삭제, 종료된 공간의 데이터는 내부 보관 30일(`purge_after`, 서버 설정값, 이용자에게 알리지 않음) 뒤 예약 작업이 완전히 삭제한다(아래 "공간 종료(소프트 삭제)와 완전 삭제").

### 공간 종료(소프트 삭제)와 완전 삭제

(2026-10-27 5차 답변, `spec.md` Decided 33~35, 모두 가정)

- **상태**: `couple_space.status`는 `active | ended`만 가진다(`recovery_pending`·`deleted` 상태는 없다. 완전 삭제된 공간은 행이 없다). 종료 때 `ended_at`·`purge_after`(= `ended_at` + 내부 보관 30일, 서버 설정값)·`ended_reason`(`ended`·`disconnect`·`account_deletion`)·`ended_by_user_id`를 기록하고, 두 `space_member.space_active`를 같은 트랜잭션에서 false로 바꾼다(이 열은 "활성 공간 하나" 부분 유일 인덱스를 위해서만 남긴다).
- **접근 차단**: 모든 RLS와 서버 함수는 `status = 'active'`인 공간만 존재하는 것으로 본다. 스냅샷, 프롬프트 세션·미리 보기·적용, 생성 장식, 홈 커버 사진(Storage 서명 주소 포함), 마일스톤, 신고, Realtime 모두 종료 즉시 막힌다. 종료된 공간의 스냅샷은 비구성원처럼 `404`다.
- **종료 알림**: 클라이언트가 종료된 공간에 대해 읽을 수 있는 유일한 정보다. `GET /spaces/mine`의 `ended`(`kind`·`by`·`at`)로만 전달하고 `POST /spaces/mine/ended/ack`로 확인한다. 공간 식별자·삭제 일정은 담지 않는다. 별도 `space_end_notice`(구성원별 한 행)에 저장하고 늦어도 완전 삭제 때 지운다.
- **완전 삭제 작업(내부, 클라이언트 API 아님)**: 예약 서버 작업 `purge_expired_spaces()`(Edge Function `lifecycle-sweep`을 스케줄러가 호출). `purge_after <= now()`인 공간마다 ① Storage 객체(홈 커버 현재 객체와 삭제 대기 목록)를 먼저 지우고 ② 그 공간의 모든 행(공간·구성원·초대·방 테마와 버전·꾸밈 요청·프롬프트 세션/메시지·홈 커버 사진·마일스톤·생성 장식·생성 시도·그 공간의 신고·일일 요청 행·종료 알림)을 한 트랜잭션으로 지운다. 공간 단위로 멱등이고 재시도에 안전하다: 파일 삭제는 "없으면 성공"으로 보고, 실패하면 공간은 `ended` 그대로(이미 보이지 않음) 남아 다음 실행에서 다시 시도한다. 부분 삭제로 보이는 상태는 없다. 내용 없는 `deletion_started`/`deletion_completed` 이벤트만 남기고 `generation_block` 지문(개인정보 없음)은 지우지 않는다. 신고 행을 증거로 오래 둘지는 열린 질문(기본 가정: 함께 삭제).
- **서비스 키**: 완전 삭제 작업은 서버 함수의 service-role로만 돌고 클라이언트에는 키가 없다.
- **문구 규칙**: 앱·설정·스토어·약관 문구는 일수와 복구를 말하지 않는다(법적 문서의 실제 동작 기술은 법률 검토 대상, `spec.md` Open Decisions 22).

**상태 기계** — `account_deletion`(사용자당 한 행, 서버 전용, 개인 내용 없음)

`state`는 **마지막으로 끝난 단계**다. 각 줄은 그 상태에서 서버가 다음에 하는 일이다.

| 상태 | 다음에 하는 일 | 끝나면 |
|---|---|---|
| `requested` | `begin_account_deletion(user_id)`가 **한 트랜잭션**으로: 사용자 `deleting` 표시 → 프로필 개인 필드(언어·시간대·화면 테마와 이름 필드가 있다면 그것)와 AI 동의 기록 비우기 → 활성 공간 종료(`end_space`, `ended_reason = account_deletion`, 상대에게만 알림 `account_deleted`) → 대기 초대 폐기 → 프롬프트 세션 점유 해제·열린 세션 닫기·진행 중 생성 요청 폐기 → 이 사용자의 세션 무효화. 행(`requested`)은 같은 트랜잭션 안에서 만들고 끝에 `space_ended`로 바꾸므로 정상 경로에서는 `requested`가 밖에서 보이지 않는다(재개 로직이 `requested`를 만나면 이 함수를 다시 돌린다, 멱등) | `space_ended` (커밋 후에만 `202`) |
| `space_ended` | 공급자 해제(Apple revoke / Kakao unlink; 이메일은 건너뜀) | `provider_revoked` |
| `provider_revoked` | Supabase 인증 사용자 삭제(`auth.admin.deleteUser(id, shouldSoftDelete=false)`) | `auth_deleted` |
| `auth_deleted` | `finish_account_deletion(user_id)`: `user_profile.status = shell`(가리키는 구성원 행이 이미 없으면 프로필 행을 바로 지움), 보관한 공급자 자격(아래)을 지움 | `done` |
| `done` | 끝. 껍데기 프로필은 종료된 공간의 구성원 행이 가리키는 동안만 남는다 | — |

- **멱등·재개**: 각 단계는 "이미 끝났으면 성공"으로 본다(Apple revoke와 Kakao unlink가 이미 해제된 경우의 오류도 성공으로 취급, 오류 형태는 구현 전 공식 문서로 확인). 단계마다 `state`·`updated_at`·`attempts`·`last_error_code`(내용 없는 코드)만 기록한다. 같은 `DELETE /account` 재시도는 `202`를 돌려준다.
- **실행기**: `DELETE /account` 핸들러가 `requested`를 동기로 끝내고 `202`를 돌려준 뒤 나머지를 같은 호출의 백그라운드(`EdgeRuntime.waitUntil`)에서 이어 간다. 안전망은 **`lifecycle-sweep` 확장**이다: 스케줄러가 주기적으로(15분, 서버 설정값 가정) 호출하면 `state != done`인 행을 백오프(`attempts`에 따라 증가)로 이어서 처리하고, 이어서 기존 `purge_expired_spaces()`를 돈다(완전 삭제는 `purge_after` 기준이라 같은 호출에서 처리해도 상관없다). 서버가 단계 사이에 죽어도 다음 실행이 `state`에서 이어서 끝낸다. 계속 실패하면(예: 시도 횟수 상한) 사용자·공간 식별자 같은 개인정보 없는 운영 경고만 남긴다.
- **완료 보장**: 어느 단계에서도 사용자는 이미 로그아웃·접근 불가이므로 지연이 이용자에게 보이지 않는다. 계정 삭제를 접수하고도 멈춘 계정은 없어야 한다(SC-011).

**공급자 해제 (단계 2)**

- **Apple (Sign in with Apple)**: 앱이 재인증 때 Apple 로그인을 다시 해서 받은 `authorizationCode`를 `DELETE /account`의 `reauth.authorizationCode`로 보낸다. 이 코드는 **짧은 수명의 일회용**이라 서버가 접수 트랜잭션(`begin_account_deletion`) **앞에서** Apple 토큰 엔드포인트로 토큰을 바꾸고(교환이 실패하면 아무것도 바뀌지 않은 채 `401 REAUTH_REQUIRED`) 접수 뒤 Sign in with Apple REST **revoke**를 부른다(Apple 요구: 토큰 해제, research.md 10.2). revoke 재시도에는 교환한 토큰이 필요하므로, 첫 시도가 실패하면 **암호화한 토큰을 `account_deletion`의 서버 전용 열에 최대 24시간만 보관**하고 성공하거나 24시간이 지나면 지운다(가정; 대안은 동기 한 번만 시도하고 실패 시 운영 경고만 남기는 것. 토큰은 로그·오류에 남기지 않는다). 토큰 해제 API 문서 본문은 확인하지 못했다(UNVERIFIED) — 구현 전에 공식 문서로 요청 형식을 확인한다.
- **카카오**: 서버 비밀 키로 연결 끊기(unlink) API(`POST https://kapi.kakao.com/v1/user/unlink`)를 부른다. 대상 카카오 사용자 ID는 Supabase 인증 사용자의 identity에서 읽는다 — 공급자 해제(단계 2)가 인증 사용자 삭제(단계 3)보다 **먼저**이므로 재시도 때도 identity가 남아 있어 따로 보관하지 않는다. 카카오는 해제 결과를 받은 뒤에 회원 탈퇴 처리하라고 하므로 성공 응답 전에는 다음 단계로 가지 않는다. 앱 키·어드민 키를 쓰는 방식과 필요한 권한(동의 항목 아님, 앱 설정)은 구현 전에 공식 문서로 확인한다(UNVERIFIED).
- **이메일**: 공급자 단계 없음. 재인증은 6자리 코드 재입력.
- **Google 로그인**은 V1에 없다(research.md 10.2).

**세션 무효화와 요청별 상태 확인**

- `begin_account_deletion`이 이 사용자의 세션을 서버 쪽에서 지운다(service-role SQL로 `auth.sessions`, 리프레시 토큰은 연쇄 삭제 — 설치된 Supabase Auth 버전에서 스키마와 동작을 구현 전에 확인한다). 필요하면 `banned_until`로 보완한다. 이미 발급된 JWT는 만료까지 유효할 수 있다(research.md 10.2: 삭제해도 기존 세션이 자동으로 로그아웃되지 않음).
- 따라서 모든 Edge Function은 공통 가드(`requireActiveUser`)에서 `user_profile.status = 'active'`를 확인해 아니면 `401`(`409 ACCOUNT_DELETING`은 변경 요청에만, 아래 API 계약), 공간 단위 RLS는 이미 공간이 `ended`라서 막혀 있고, 공간이 없는 개인 설정 RLS(`/profile/preferences` 등)도 `status = 'active'` 조건을 둔다. Realtime 구독은 공간 종료와 세션 무효화로 끊긴다.
- 클라이언트는 `202`를 받으면 로컬에서 바로 로그아웃하고 예약 알림을 모두 취소하며 로컬 캐시(공간·사진·장식)를 지운다.

**껍데기 프로필과 외래 키**

- `user_profile.user_id`는 `auth.users`에 **외래 키를 걸지 않는다**(걸면 인증 사용자 삭제가 막히거나 연쇄 삭제로 구성원 행까지 지워진다). 인증 사용자가 지워진 뒤에도 이 UUID는 불투명한 식별자로만 남고 다시 쓰이지 않는다. 같은 로그인으로 재가입하면 새 인증 사용자·새 `user_id`다.
- 공간 범위 테이블(`space_member`, 요청·메시지·생성 장식·신고 등)의 `*_user_id`는 `user_profile(user_id)`를 `ON DELETE RESTRICT`로 참조한다. 계정 삭제 시 활성 공간은 종료되므로 이 참조 행은 모두 종료된 공간에 있고, `purge_expired_spaces()`가 공간 행을 지운 뒤 같은 트랜잭션에서 **`shell` 상태이고 어떤 `space_member`도 가리키지 않는 프로필**을 지운다. 한 사람이 종료 후 새 공간을 만들고 30일 안에 계정을 지우면 껍데기가 여러 공간에 걸쳐 남을 수 있고 마지막 공간이 퍼지될 때 사라진다.
- `SpaceLifecycleEvent.actor_user_id` 같은 내용 없는 감사 열은 외래 키가 없다. 껍데기를 지울 때 해당 사용자 ID를 null로 바꾼다(가정).
- AI 동의 기록은 `space_member`의 열이므로 `begin_account_deletion`이 이 사용자의 모든 구성원 행에서 지운다(기본 가정, 법률 검토가 최소 로그를 요구하면 식별 불가한 형태로 보관, Open Decisions 27).

**Storage 소유자 주의 (`deleteUser` 차단)**

Supabase는 **Storage 객체의 소유자인 사용자를 삭제할 수 없다**(research.md 10.2). 우리 구조는 서버가 재인코딩한 사본만 서비스 권한으로 저장하므로 영구 객체의 `owner`가 사용자가 아니다. 업로드 주소로 사용자가 직접 올린 원본 임시 객체가 있다면 `owner`가 설정되는지 구현 전에 확인하고, 설정된다면 서버가 받아서 서비스 권한으로 올리게 바꾸거나 단계 1에서 임시 객체를 먼저 지운다. 테스트로 모든 Storage 객체의 소유자가 비어 있음을 확인한다(quickstart H).

**경계 사례**(스펙 US10·엣지 케이스와 같다): 혼자인 사용자(공간 종료, 알림 없음) · 보유한 대기 초대 코드(폐기) · 점유·열린 프롬프트 세션(해제) · 오프라인(클라이언트에서 막음, 큐 없음) · 같은 로그인으로 즉시 재가입(새 빈 계정, 재가입 차단은 열린 질문) · 완전 삭제 작업과 상대의 종료·연결 끊기와의 경합(**공간 행 잠금 하나**, 이미 종료·퍼지된 공간의 `end_space`는 아무 일도 안 함, 먼저 성공한 이유가 알림을 정함) · 서버 재시작(단계에서 이어서).

**웹 삭제 페이지와 스토어 공개**

- Google Play 요구: 앱 안 경로 + 앱 밖 웹 링크(데이터 보안 양식에 입력). 소유자가 `aroom.jinjinstar.com/delete-account`(자리표시)에 정적 페이지를 만든다. 본문 사양은 `docs/account-deletion-web.md`(태스크). 앱을 열 수 없는 사람의 요청은 가입 이메일 회신으로 본인 확인하는 수동 운영 절차(가정, `docs/operator-review-runbook.md`에 절 추가, 법률·운영 검토). 공개 지원 이메일은 아직 없다.
- Apple 심사 메모: 경로(설정 > 계정 삭제), 재로그인 확인, Sign in with Apple 토큰 해제, 공유 공간 콘텐츠의 처리·보관 안내. 개인정보 처리방침: 즉시 삭제·익명화되는 항목과 최대 30일 내부 보관 항목(법률 검토).
- **위험(솔직히)**: Apple은 공유 사용자 생성 콘텐츠도 계정과 함께 삭제되길 기대하고 법적 보관 정보는 알리라고 한다. 우리의 내부 30일은 법적 보관이 아니라 운영상 보관이라 심사·방침에서 문제가 될 수 있다. 대안은 계정 삭제 경로에서만 공간을 즉시 완전 삭제하는 것이다(`spec.md` Open Decisions 26, 게이트 G18에서 소유자가 정한다).

### 홈 커버 사진

V1에서 허용하는 유일한 사용자 사진이다(spec FR-032~FR-039). 장면 문서·AI 문맥과 분리된 별도 경로로 다룬다. 공유(마지막 변경 우선, 변경자 표시)·공간 종료 시 즉시 열람 불가와 완전 삭제 때 파일 삭제·검수/신고 없음과 형식·크기·정리 시점(JPG·PNG·HEIC, 20MB, 비율 고정 자르기, 서버 재인코딩, 이전 파일 24시간 뒤 삭제)은 모두 승인된 결정이다. 최종 개인정보 처리방침 문구만 법률 검토가 필요하다.

- **저장**: Supabase Storage의 **비공개 버킷**(`home-covers`, Seoul 리전). 객체 경로는 `{space_id}/{cover_id}.jpg`처럼 공간 ID로 범위를 나눈다. 공개 URL은 만들지 않고, 앱은 RLS로 권한이 확인된 **서명된 URL**(짧은 수명, 예: 1시간)로만 이미지를 받는다. 서명된 URL은 로그·분석에 남기지 않는다.
- **접근 통제(RLS)**: `storage.objects` 정책은 해당 `space_id`의 **활성** 공간 구성원에게만 읽기·쓰기·삭제를 허용한다(종료된 공간의 사진은 서명 주소 발급이 거절되어 즉시 읽을 수 없다. 종료 화면은 사진이나 공간 데이터가 아니라 종료 알림(`GET /spaces/mine`의 `ended`)만 쓴다). 클라이언트에 service-role 키를 두지 않는다. 업로드 전 서버 함수가 구성원·공간 상태를 확인하고 일회용 업로드 주소를 발급한다.
- **형식·크기 제한**: JPG·PNG·HEIC, 원본 20MB 이하(승인). 시스템 사진 선택기(iOS PHPicker, Android Photo Picker)를 써서 사진 보관함 접근 권한을 받지 않는다. 앱은 자르기 영역(커버 비율 고정)을 적용해 긴 변을 제한한 JPG(또는 WebP)로 재인코딩한 뒤 올린다. 서버 함수가 형식·크기·실제 이미지 헤더를 다시 검사하고 다시 인코딩된 사본만 저장한다(HEIC 변환과 최대 해상도는 구현 단계에서 확정).
- **EXIF·메타데이터 제거**: 위치(GPS)·기기 정보·촬영 시각 등 EXIF/XMP를 저장본에서 제거한다. 앱 재인코딩과 서버 재인코딩 중 서버 결과만 신뢰한다.
- **교체·삭제**: 새 사진이 정상 저장된 뒤에만 `HomeCoverPhoto.current_object`를 바꾸는 트랜잭션을 실행하고 이전 객체를 삭제 대기 목록에 넣는다(실패해도 기존 사진 유지). 교체·삭제로 남은 이전 파일은 새 사진 저장이 확인된 뒤 삭제 대기 목록에 넣고 **24시간 뒤 삭제**한다(승인된 계획 값, 미적용 preview 보관과 같은 기준). 공간의 완전 삭제 작업(`purge_expired_spaces`)이 현재 객체와 대기 목록까지 먼저 지우고 그다음 행을 지운다.
- **동기화**: 변경은 Realtime에 `cover_id` 변경 알림만 보내고 상대는 서명된 URL을 새로 요청한다. 마지막 변경 우선(결정)은 `version`과 서버 시각으로 판단하고, `uploaded_by_user_id`를 홈에 보여 준다(누가 바꿨는지).
- **오프라인**: 마지막으로 받은 사진을 캐시(용량·LRU 제한)해서 보여 주고, 변경은 온라인 전용이다.
- **AI·장면과 분리**: 사진 URL, 객체 경로, 픽셀은 프롬프트·장면 문서·`room-scene.schema.json`·AI 요청에 포함되지 않는다. 장면 검증기는 사진 참조 필드를 거부한다.
- **검수와 신고 없음(결정)**: 사진 검수(자동·수동)와 사진 신고 기능은 두지 않는다. 신고·연결 끊기 화면의 대상에 사진은 없다. 이용자 생성 콘텐츠 정책(Apple 1.2, Google Play UGC)에 비공개 두 사람 공간의 사진을 어떻게 설명할지는 법률 검토에서 확인한다(spec Open Decisions 1).
- **접근성·대비**: 사진 위 글자는 앱이 어두운 막과 면을 깔아 대비를 지킨다(디자인 `components.md` 홈 커버). 사진은 장식으로 취급한다.

**저장소**: 확정 — Supabase Postgres(관계형 데이터)와 Supabase Storage 비공개 버킷(홈 커버 사진 한 장). 커플 공간·초대·동의·테마 버전은 관계형 행으로, 확정 테마 스냅샷은 버전이 붙은 JSONB로 저장한다. 로컬은 마지막 확정 스냅샷과 필요한 라이선스 에셋을 캐시한다.

**테스트**: 구현 단계에서 장면/JSON Schema 단위 테스트, 보호 영역 기하 테스트, API 계약 테스트, 두 사용자 권한·동기화 통합 테스트, iOS/Android 기기 UI 및 EAS 내부 빌드 검증을 작성한다. 이 계획 단계에서는 테스트나 앱 코드를 만들거나 실행하지 않는다.

**대상 플랫폼**: iOS 및 Android 휴대전화. 태블릿/웹/PWA는 범위 밖이다.

**성능 목표(제안)**: 장식 16개와 문구 3개까지 60fps 목표를 중급 지원 기기에서 검증한다. 캐시된 장면 첫 표시 1초 이내를 목표로 하며, 서버 AI 응답에는 네트워크 변동이 있으므로 사용자에게 진행/실패 상태를 제공한다. 실제 성능 기준은 디자인 완료 후 프로토타입에서 확정한다.

**제약**: 공유 방은 서버 권한검사 및 동시 편집 제어가 필요하다. 앱은 오프라인에서 마지막 확정 장면과 D-day를 읽기 전용 표시한다. 모델 출력은 서버와 클라이언트가 동일한 스키마·안전 규칙으로 검사한다.

**규모/범위**: 커플 공간당 구성원 2명, 카탈로그 24~36개(현재 디자인은 24개, 마일스톤 제안도 새 오브젝트 0개; 프롬프트로 만드는 생성 장식은 카탈로그와 별개로 커플 보관함에 둔다), 씬당 오브젝트 최대 16개와 짧은 텍스트 최대 3개, 홈 커버 사진 최대 1장(원본 20MB 이하 가정), 마일스톤 보이는 기간 7일, 마일스톤 알림 예약 기기당 최대 3개(둘 다 결정). 꾸미기 요청 성공 최대 3회/커플/일(방 시간대 자정 초기화), 생성 장식 보관함 커플당 30개(가정), 요청당 새 장식 최대 2개(가정).

### 마일스톤 축하 (P2, 앱 안 축하 + 옵트인 기기 예약 알림)

- **계산**: 서버가 방의 시간대와 `anniversary_date`로 오늘을 구하고 마일스톤을 판단한다. 일수 마일스톤은 50·100·200·300·500·1000일(당일 = 1일째), 주년은 **함께한 날짜와 같은 달력 날짜**(매년, 2월 29일 시작은 평년 2월 28일)다. 같은 날 겹치면 주년 하나만 만든다(`priority`). 마일스톤을 위한 별도 스케줄러 없이(공간 완전 삭제 예약 작업은 별개다) `GET /milestones/current` 호출 때 필요한 `MilestoneCelebration` 행을 멱등하게 만든다(유일 `(space_id, milestone_key)`). 보이는 기간은 당일부터 7일(결정, 주년 포함)이고 지나면 `passed`다. 목록·N은 서버 설정 상수다.
- **구성원별 확인**: `MilestoneSeen`(구성원 본인 행만 RLS). 카드·말풍선을 닫으면 `POST …/seen`, 오프라인이면 기기 큐에 저장했다가 연결 후 전송(멱등). 상대 확인 상태는 서로 읽지 않아 Realtime이 필요 없다. 앱을 열 때와 방 탭에 들어갈 때 `GET /milestones/current`를 한 번 호출한다.
- **함께한 날짜 변경**: `PATCH /anniversary` 트랜잭션 안에서 기록된 마일스톤의 새 `milestone_date`를 계산해 오늘보다 뒤인 것의 행과 확인 기록을 지운다(`milestonesReset`으로 알림). 나머지는 그대로 둔다. 클라이언트는 응답을 받으면 알림을 다시 예약한다.
- **알림(옵트인, 기기 예약 로컬 알림)**: `expo-notifications`의 로컬 예약(`scheduleNotificationAsync`, 날짜 트리거)만 쓴다. **서버 작업·푸시 토큰·APNs/FCM 설정이 없다.** 기기는 `GET /milestones/current`의 `upcoming`(최대 3개)을 받아 마일스톤 당일 오전 9시(방 시간대)로 예약하고 알림 식별자를 마일스톤 키로 써서 중복을 막는다. iOS의 대기 알림 64개 한도는 3개 예약이라 문제 없다. 재예약 트리거: 함께한 날짜 변경, 방 시간대 변경, 앱 업데이트, 앱을 열어 목록 확인. 취소 트리거: 공간 종료, 연결 끊기, 로그아웃, 알림 끄기, 상대가 종료·연결을 끊은 것을 종료 알림으로 알게 된 때(종료된 공간의 예약은 되살리지 않는다). 알림 설정(켜짐 여부)은 기기 로컬 저장소에만 두고 서버에 저장하지 않는다.
- **권한 흐름**: 앱 첫 실행에서는 권한을 묻지 않는다. 구성원이 처음 본 축하 카드를 닫은 직후 사전 안내 시트를 한 번 띄우고("다음에"면 다시 띄우지 않음), "알림 켜기"를 눌러야 OS 권한 창을 부른다. 설정의 알림 행에서도 켠다. 권한이 거절·해제되면 행이 "기기에서 꺼져 있음" + 기기 설정 열기로 바뀐다. Android 13+는 `POST_NOTIFICATIONS`, iOS는 알림 권한. 알림 채널은 하나(마일스톤).
- **알림 문구와 열기**: 제목 = 앱 이름, 본문 = 고정 한 문장("아루미가 축하할 일이 생겼어요.", ko/en/ja), 이름·날짜·일수를 넣지 않는다(잠금 화면). 알림을 누르면 딥 링크로 홈이 열리고 `GET /milestones/current`로 축하 카드를 보여 준다. 이미 본 마일스톤이면 홈만 연다.
- **스토어·개인정보 메모**: 알림은 사용자가 켠 로컬 알림이고 마케팅이 아니다. 알림 권한 사용 목적 문구를 적고, 서버에 토큰을 저장하지 않으며 문구에 개인정보가 없다는 점을 심사 메모에 쓴다. 개인정보 처리방침 문구는 법률 검토에서 확인한다. 서버 푸시는 범위 밖(spec Open Decisions 4).
- **기념 제안(프리셋)**: 서버 코드의 상수(`milestone-day`: 케이크·풍선·리본·반짝이 2 + 기념 문구 / `milestone-anniversary`: 선물 추가)이고 카탈로그 기존 오브젝트만 쓴다. 기존 배치 알고리즘과 장면 검증기(16/3 한도, 보호 영역)를 거쳐 후보 장면을 만들고, 기존 `DecorationRequest`(`source: milestone_preset`)로 저장해 confirm 경로를 그대로 쓴다. 우선순위: 케이크 → 리본 → 풍선 → 반짝이 → 선물 → 문구 순으로 자리가 있는 만큼만 놓는다.
- **AI·비용**: 호출하지 않는다. 동의 확인과 일일 3회 계수에 포함하지 않고 AI 요청 이력에도 남기지 않는다. 대신 정형 감사 이벤트(`milestone_preset_previewed`/`_applied`, 키만)를 남긴다.
- **클라이언트**: 홈 카드·방 말풍선·제안 입구·알림 사전 안내 시트·설정 알림 행 컴포넌트. 마스코트 `cheer` 포즈와 앱 고정 움직임(2.4초 통통, 1.4초 반짝임)은 앱 코드가 정하며 동작 줄이기에서 정지한다. 새 에셋은 없다(카탈로그 24개 그대로).

### 생성 오브젝트 (P2) — 새 배경·말풍선 장식 (2026-10-27 · 모두 가정)

소유자는 "프롬프트로 새 오브젝트가 만들어져 DB에 저장되어 모든 커플의 방이 다르길" 바랐고, 규칙(품질 수준 이상만, 저작권 요소 금지, 배경·말풍선 꾸미기 용도)을 두자고 했다. 안내했던 세 선택지(A 지금처럼 24개 배치만 / B 더 큰 카탈로그+매개변수 / C AI가 새 벡터 오브젝트를 만들어 검증 후 커플별 저장) 중 C로 해석했다. **MVP에는 들어가지 않고 MVP 바로 다음 단계(P2)**이며 소유자가 앞당길 수 있다. 안전 문서는 [ai-guardrails.md](./ai-guardrails.md), 정책 확인은 research.md 9장.

- **범위**: 세 종류 — 배경 조각(`background_piece`: `wall | floor | backdrop | window_view`), 말풍선 틀(`bubble_frame`), **방 소품**(`prop`: `floor | wall | shelf`, 2026-10-27 소유자 결정). 소품은 더 엄격하다: viewBox 256 이하·도형 30개 이하·복잡도 45 이하, 얼굴 닮음 휴리스틱(`PROP_FACE_LIKE`)과 프롬프트의 마스코트·앱 캐릭터·글자·로고·브랜드 거절, 장면 16개 한도에 포함. 마스코트·캐릭터·사진·텍스트가 들어간 그림은 만들지 않는다. 마스코트 규칙(FR-018)은 그대로다.
- **형식 선택(제안, 대안 포함, 결정자 소유자)**: 권장안은 **허용목록 JSON 도형 목록**(`aroomi-shape-v1`, `contracts/generated-object.schema.json`). 이유: ① SVG 문자열은 파서·스크립트·외부 참조·CSS 공격면이 크고 "모델이 만든 데이터가 코드가 되지 않는다"(헌법 II)를 지키기 어렵다, ② 서버가 모든 값을 좌표·색·개수 단위로 검사·정규화할 수 있다, ③ 앱은 새 코드를 받지 않고 미리 컴파일된 고정 렌더러가 값을 그린다(스토어 심사 메모와 맞음). 대안 — (a) 안전한 SVG 부분집합: 사람이 읽기 쉽지만 부분집합 파서를 직접 만들어야 한다. (b) 매개변수형 템플릿(옵션 B): 가장 안전하고 품질이 예측 가능하지만 "새로 만든다"는 느낌이 약하다. (c) 래스터 이미지 생성: 사진 같은 이미지·권리 위험이 커서 제외. 한계: JSON 도형만으로 모델이 일관되고 매력적인 그림을 낼지는 **측정 전**이다(research.md 9장).
- **렌더링**: React Native Skia에서 검증된 값으로 그린다. `path`는 SVG 문자열 파서에 넘기지 않고 허용된 명령(M L H V C Q Z)을 앱이 직접 파싱해 Skia 경로를 만든다(문자열 파서의 예외 문법을 쓰지 않으려고). 윤곽선·크림 림은 렌더러 규칙이므로 문서에 없다. 같은 입력은 같은 그림을 낸다(결정적). 렌더 직전에 검증기를 한 번 더 돈다(저장 뒤 검증기 버전이 올라간 경우 대비).
- **기준 라이브러리 번들**: `design/reference-library/`의 레퍼런스 JSON과 스타일 규칙을 빌드 때 `supabase/functions/_shared/reference-library/`로 복사하고 버전(`style_reference_version`)을 단다. 요청마다 스타일 앵커로 모델에 준다(프롬프트 캐시 대상).
- **파이프라인(서버, `decoration-previews` 함수 안)**: ① 권한·동의·공간 활성·킬 스위치·보관함 여유·시도 한도 → ② 입력 정책(결정론적 필터: 길이·URL·전화번호·`@`·QR 요청 + 분류 호출 `allow|refuse(category)`) → ③ 생성 호출(구조화 출력: 카탈로그 배치 + 생성 문서 ≤2 + 텍스트) → ④ 형식 검증·정규화(공유 검증기, 팔레트·한도·대비·스타일 적합도) → ⑤ 2차 검사(별도 호출: 프롬프트+결과 JSON+정책 → `pass|fail(category)`) → ⑥ 후보 저장(`candidate`) → ⑦ 성공 때만 횟수 증가·응답. 검증·2차 검사 실패는 오류 피드백과 함께 **한 번** 재시도하고(입력 정책 거절은 재시도 없음) 그래도 실패하면 `503 GENERATION_FAILED`. 모든 단계 결과를 `GenerationAttempt`에 남긴다(원문 모델 출력은 저장하지 않음).
- **모델·비용 모델(가정)**: 입력 정책 분류·2차 검사는 Haiku 5.5, 생성은 Haiku 5.5 기본에 품질 실패 사례에 한해 Sonnet 5.5 제한 승급(기존 정책 유지). 가격은 research.md의 접근일(2026-10-24) 가격표 값($0.10/$0.50, $2/$10 per MTok; 캐시 읽기 10%, 캐시 쓰기 1.25배는 재확인 필요)을 쓴 **추정**이고 토큰 수는 측정 전이다:

  PoC의 월 $100 포함 크레딧으로는 Haiku 기준 커플당 월 약 $0.2(= $0.0066×30) 정도라 수백 커플도 감당하지만, 전부 Sonnet이면 커플당 월 약 $3이라 약 30커플이 한계다. **그래서 승급은 품질 실패 사례에 한정**한다(기존 정책 그대로). 캐시 쓰기·세금·재시도·저장소는 제외했고 실제 프롬프트·렌더 결과로 측정해야 한다(게이트 G17의 일부).
- **오류 경로**: 입력 거절 → 422 `GENERATION_REFUSED`(횟수 안 씀) · 검증/2차 검사 실패 → 재시도 1회 → 503 `GENERATION_FAILED`(안 씀) · 제공자 장애/지연 → 503 + 재시도 가능(안 씀) · 킬 스위치 → 503 `GENERATION_DISABLED` · 보관함 가득 → 409 `LIBRARY_FULL`(모델 호출 전) · 시도 한도 → 429 `RATE_LIMITED` · 일일 한도 → 429 `DAILY_LIMIT_REACHED`. 어느 경우에도 공유 방과 현재 버전은 그대로이고 두 사람이 같은 대화에서 결과 메시지를 본다.
- **저장·수명**: `GeneratedObject`(불변, 커플 보관함 상한은 서버 설정값 — 기본 40은 가정. 저장은 장식당 12KB 이하 JSONB라 40개도 약 0.5MB 이하, 목록은 2열 스크롤로 40개까지 감당, 하루 최대 3번 성공×요청당 2개로 약 7일치. 지우면 방에 놓인 것도 방에서 사라진다. 하루 한도와 상한은 설정값이라 나중에 요금제에 연결할 수 있으나 지금은 요금제·결제·권한을 설계하지 않는다), 후보는 24시간, 공간 종료 시 즉시 읽을 수 없고 완전 삭제와 함께 삭제, RLS는 활성 공간 구성원의 읽기만, 쓰기는 서버 함수만. 별도 Storage 객체는 쓰지 않는다(JSONB 12KB 이하).
- **원격 설정과 킬 스위치**: `app_config`의 `generation_enabled`(새 생성)와 `generated_render_enabled`(생성 장식 렌더링)를 서버가 요청마다 읽고 앱은 스냅샷 `features`로 받는다. 앱 업데이트 없이 끌 수 있다.
- **클라이언트**: 장식 상세 시트(방에서 장식 누르기), 우리 장식 보관함 시트(프롬프트 화면 안: 다시 쓰기 칩·지우기), 거절·실패·킬 스위치·보관함 가득 상태, 미리 보기의 "새로 만든 장식" 표시. 새 화면 번호는 만들지 않고 기존 화면(S07·S08·S09·S15)의 상태와 시트로 둔다.
- **위험과 정직한 한계**: ① 가드레일은 저작권 위험을 줄일 뿐 없애지 않는다(스타일 적합도 검사는 "우리 스타일에 가까운가"이지 "남의 것과 닮았는가"가 아니다). ② AI 결과의 저작권·소유권은 법적으로 불확실하다(FR-025·FR-068). ③ Haiku급 모델이 이 형식으로 일관되고 매력적인 장식을 만드는지는 측정 전이다 — 첫 스프린트에 실제 모델로 30개 프롬프트 평가를 해서 실패하면 옵션 B(매개변수형 템플릿)로 후퇴한다. ④ 렌더 이미지를 보고 판단하는 2차 검사는 없다(텍스트·구조 기반 검사만; 서버 래스터 렌더 필요, 열린 질문). ⑤ 신고 처리는 PoC에서 수동이다.

### 신고 확장 (P2, 생성 장식·방 전체)

- 기존 `report`를 확장한다: `target`에 `generated_object`, `reason`에 `copyright`, 신고자 숨김(`hidden_for_reporter`), 검토 결과(`outcome: removed|kept`), 신고자 알림 기록. `GET /reports/mine`·`POST /reports/{id}/seen`이 신고자 상태 표시를 맡는다.
- **즉시 효과**: 접수와 같은 트랜잭션에서 신고자의 읽기에서만 그 장식을 걸러낸다(상대는 운영 검토 전까지 그대로 본다. 두 사람 화면이 잠시 다를 수 있다 — 의도된 동작이고 상세 시트에 "내 화면에서만 숨겼어요"라고 알린다).
- **운영 흐름(PoC, 수동)**: 운영자가 서버 전용 `review_report`로 결정한다. `removed`이면 장식이 `removed_by_operator`가 되어 두 사람 읽기에서 걸러지고 프롬프트 지문이 `GenerationBlock`에 들어가 같은 요청은 입력 정책에서 거절된다. 절차 문서는 `docs/operator-review-runbook.md`(태스크로 만든다). 응답 시간 목표·담당자는 열린 질문이다.
- **개인정보**: 신고 메모·사유는 상대에게 보이지 않고, 운영자는 대상 장식 데이터와 관련 프롬프트만 읽는다. 신고 남용은 사용자당 하루 10건 한도.
- **연결 끊기와 별개**이며 홈 커버 사진은 대상이 아니다(사진 신고는 열린 질문).

## 헌법 확인

### 설계 전 게이트

- 사용자 안전·개인정보: 동의와 최소 전송 데이터를 별도 엔티티로 보존한다. AI 자격 증명은 서버에만 둔다. 통과.
- 결정론적 경계: 모델은 도구 없이 구조화된 데이터만 반환하며 검증 전후 미리보기에 표시하지 않는다. 통과.
- 접근성·이해 가능성: D-day와 컨트롤은 네이티브 접근성 뷰이며, 미리보기/확인/취소를 명시하고, 종료·삭제의 결과를 확인 단계에서 분명히 알린다. 통과.
- 검증 가능한 변경: 장면 스키마, API, 상태 전이, 검증 계획을 계약 문서로 정한다. 통과.
- 단순한 설계: 적용은 되돌릴 수 없는 한 방향 동작으로 두고(적용 전 미리 보기·확인·취소가 안전장치), 열린 대화 안에서는 이전 후보로 되돌릴 수 있다. 마이그레이션 가능한 스키마 버전을 사용한다. 통과.

### 생성 오브젝트·신고 확장의 헌법 확인 (2026-10-27)

- I 사용자 안전·개인정보: 프롬프트는 AI에 보내는 정보로 기존 동의 범위(FR-016) 안에서만 쓰고, 입력 정책·2차 검사를 위한 추가 호출도 같은 범위다. 남용 대응용 프롬프트·판정 보관(30일 가정)은 개인정보 처리방침에 넣어야 한다(열린 질문, 법률 검토). 신고 내용은 상대에게 노출하지 않는다. 통과(법률 검토 조건부).
- II 결정론적 경계: 모델이 만든 것은 **데이터**(허용목록 JSON)이고 코드·SVG·URL이 아니다. 서버가 검증·정규화한 값만 저장·전달하고 클라이언트는 고정 렌더러로 그린다. 입력 정책·2차 검사도 모델의 판정이 아니라 서버가 집행한다. 통과.
- III 접근성: 말풍선 글자 대비 4.5:1을 검증기가 강제하고, 생성 장식은 장식(읽기 순서 제외)이며, 거절·실패·킬 스위치·신고 상태에 복구 경로(다시 시도·대안 제안·내일)를 보여 준다. 통과.
- IV 검증: 형식 스키마·악성 샘플·레드팀 세트·횟수 의미·RLS·신고 흐름·킬 스위치를 테스트 먼저 태스크로 둔다. 통과.
- V 작고 되돌릴 수 있는 설계: 새 저장 데이터(`generated_object` 등)는 불변 행 + 삭제 정책(후보 24시간, 공간 종료 후 완전 삭제 때 함께 삭제, 킬 스위치로 렌더 끄기)을 갖는다. 형식이 불안하면 옵션 B로 후퇴할 수 있게 장면은 참조만 저장한다. 통과.

### 5차 답변(복구 기능 제거)의 헌법 확인 (2026-10-27)

- I 사용자 안전·개인정보: 종료한 공간의 개인 데이터(사진 파일 포함)는 즉시 읽을 수 없고 내부 보관 30일 뒤 완전 삭제된다. 법적 문서는 이 실제 동작을 적어야 하는지 법률 검토가 필요하다(`spec.md` Open Decisions 22). 계정 삭제 기능은 7차 답변에서 설계했다(아래 "계정 삭제의 헌법 확인", Apple 5.1.1(v)). 조건부 통과.
- V 작고 되돌릴 수 있는 설계: **삭제 정책 = 소프트 삭제 + 내부 완전 삭제**. 이용자 복구 기능이 없어 상태가 `active | ended` 둘뿐이고(복구 대기·복구 권한·복구 차단 규칙이 사라져 단순해진다) 종료는 이용자에게 되돌릴 수 없다는 점을 확인 단계에서 분명히 알린다. 서버는 내부 보관 기간 동안 데이터를 두지만 이를 이용자 기능으로 약속하지 않는다. 완전 삭제는 멱등·재시도 안전한 예약 작업이다. 통과.

### 계정 삭제의 헌법 확인 (2026-10-27)

- I 사용자 안전·개인정보: 개인 데이터(로그인 식별자·프로필·동의 기록)는 접수 즉시 지우거나 익명화하고, 공간은 즉시 읽을 수 없게 한다. 종료된 공간의 내부 30일 보관과 껍데기 프로필은 처리방침에 실제 동작대로 적어야 하며(법률 검토) Apple의 "공유 콘텐츠도 함께 삭제" 기대와 어긋날 위험이 있다(Open Decisions 26·30). 공급자 토큰은 로그·오류에 남기지 않고 보관 시 암호화·24시간 상한. **조건부 통과**(법률·심사 확인, 게이트 G18).
- II 결정론적 경계: 삭제는 모델이 관여하지 않는 서버의 결정론적 상태 기계이고 AI에는 아무 데이터도 보내지 않는다. 공급자 호출은 서버 비밀 키로만 하며 앱에는 키가 없다. 통과.
- III 접근성: 결과 설명·체크·재인증·진행·실패·오프라인 상태를 모두 화면과 키로 설계하고(S13 상태, `acct.*`), 되돌릴 수 없다는 점을 확인 단계에서 분명히 쓴다. 통과.
- IV 검증: 상태 기계·공급자 모의(Apple revoke, Kakao unlink)·재개·경합·세션 거부·Storage 소유자·재가입 빈 계정을 테스트 먼저 태스크로 둔다(T151~T154). 통과.
- V 작고 되돌릴 수 있는 설계: 삭제 자체는 되돌릴 수 없는 한 방향 동작이다(복구 기능 제거와 같은 방침). 대신 안전장치(결과 설명·체크·재인증), 단계별 기록과 재개, 껍데기 프로필의 참조 기반 정리로 작게 유지한다. 유예 삭제는 열린 질문으로만 남긴다(Open Decisions 23). 통과.

### 설계 후 재검토

엔티티와 API 계약은 별도 파일에 고정하며, 서버 검증·클라이언트 렌더 전 검증을 함께 요구한다. 데이터 계약에서 기능 코드나 외부 URL을 배제하고, 앱의 고정 기능과 모델의 표현 제안을 분리했다. 위 원칙과 충돌하지 않음 — 통과.

## 구현 전 필요한 결정

2026-10-26 2차 답변으로 이전 목록의 대부분이 결정됐다(`spec.md` Decided 10~22; 3차 답변 23~26은 2026-10-27, 종료 뒤 복구 규칙·로더 창문·성공 기준 수치를 가정으로 결정 — **23·24는 5차 답변 33으로 대체됨**; 5차 답변 33~36은 2026-10-27, 복구 기능 제거·소프트 삭제·내부 30일 뒤 완전 삭제·종료 알림·계정 삭제 자리표시 가정(결정 36은 7차 답변 결정 42로 구체화됨); 7차 답변 41~46은 2026-10-27, 계정 삭제를 V1(P1)에 넣고 효과·상대 안내·실수 방지·공급자 해제 순서·웹 삭제 페이지를 가정으로 정함). 결정된 것: Supabase 조직·프로젝트 소유(개인 계정, 무료 플랜, 서울 리전) · 개발·PoC AI 비용(Max 요금제 포함 월 $100 API 크레딧 + 서버 비밀 Console 키, 키는 저장소·로그·앱에 두지 않는다) · 초대받은 사용자의 기존 공간 동시 가입(**불허, 한 사용자 한 활성 공간**; 종료된 공간은 세지 않음) · 최소 연령(**만 14세**) · 점유 유휴 3분과 비점유자 읽기 전용 · 마일스톤 값 · 개발자 계정 소유 주체(**개인**) · 앱 아이콘(A) · 이메일 로그인·초대 코드 형식 · 하루 한도(3회, 2026-10-27에 5회에서 줄임) · bundle ID와 도메인 제안(`com.jinjinstar.aroom`, `aroom.jinjinstar.com`, 가정).

**운영 지출 상한은 구현 전 필요 목록에서 빼서 출시 전 결정으로 옮겼다**(개발 중에는 Max 요금제 포함 API 크레딧과 무료 플랜; 공개 출시 전 유료 크레딧 전환·약관 확인은 출시 전 결정). 아래는 **정말 열려 있는 것**만 남겼다.

1. **법률 검토**: 대한민국 AI 표시·개인정보 국외 이전 동의, 최소 연령 문구, 사진 개인정보 처리방침 최종 문구와 스토어 UGC 설명, 개인정보 처리방침 전반(spec.md Open Decisions 1·6).
2. **이름 확인(확인 항목, 아직 확인 전)**: 앱 이름 아룸(Aroom)·캐릭터 이름 아루미(Aroomi)의 상표, 앱스토어·Google Play 이름 사용 가능 여부, 도메인 `aroom.jinjinstar.com` 생성. **확인 전에는 bundle ID를 스토어에 등록하지 않는다.** '아룸'이 한국어 '아름'(아름다움)·영어 'a room'과 소리가 가까운 점도 카피·스토어·검색 맥락에서 확인한다(법률 판단 아님). 공개 지원 이메일 주소가 필요하지만 아직 없다.
3. **스토어 규칙 재확인**: 이름·부제 글자 수와 심사 규칙, 연령 등급 설문, "연결 끊기 + 신고"가 악성 이용자 차단·신고 기대를 충족하는지(이 앱의 콘텐츠는 두 사람 사이 비공개라 위험이 낮다).
4. **원어민 검수**: 영어·일본어 문구(영어 "Disconnect"·일본어 "つながりを終了" 초안 포함).
5. **카카오·Apple 공식 에셋·SDK** 교체.
6. **폰트 번들 크기 실측**(EAS 산출물 기준, 권장 9파일 ≈16.4MB 압축 전)과 폰트 family/weight, 낮/밤 tokens와 license notices.
7. **에셋 최종 포맷**(PNG-8 또는 WebP 무손실). 마스코트 그림은 소유자가 생성형 AI 도구로 만든 마스터를 그대로 쓴다(일러스트레이터 재작업 없음, 약한 저작권 보호 위험 수용; 닮음 검사·법률 검토는 출시 전 권장이며 막지 않고 생성 기록은 선택 항목). 카탈로그는 방 안 마스코트 포즈 6 + 일반 오브젝트 18 = 24개다(`design/assets-spec.md`).
8. **공개 출시 전 AI 이용 약관 확인**: (1) 크레딧을 연결할 때 보이는 **프로그램 약관 원문**과 현재 **Commercial Terms**를 읽고, 포함 크레딧을 공개 소비자 앱에 써도 되는지 **Anthropic 지원팀에 서면으로 문의**한다(답을 받기 전에는 PoC 전용으로 본다). (2) 만 14세 이상이 쓰는 소비자 앱이 **Usage Policy**(그리고 지원 지역 정책)에 맞는지 확인한다(미성년자 보호 조항이 적용되는지는 **미확인**). (3) **AI 제안이 틀릴 수 있다는 앱 안 안내 문구**(사실적 주장은 따로 확인하라는 취지)를 문구 항목으로 정한다 — 법률 검토와 함께 정하며, 지금 화면에는 넣지 않았고 키 수도 바꾸지 않았다("AI 배지를 두지 않는다"는 기존 요구와의 관계도 이때 정리). (4) 포함 크레딧은 주기마다 소멸하고 잔액 0이면 요청이 멈추므로 공개 출시 전에 **유료 크레딧·결제 설정**을 한다. 참고(법률 의견이 아님, 지휘 쪽이 공개 페이지로 확인): 크레딧 페이지·도움말은 크레딧을 "자기 앱과 에이전트를 만드는 데" 쓴다고만 하고 상업 이용 금지를 적지 않았으며, 크레딧 약관(양도·환불 불가·소멸)도 상업 이용에 침묵한다. Commercial Terms A.1은 API로 고객의 최종 사용자에게 제공하는 제품을 돌리는 것을 허용하되 Usage Policy·지원 지역 정책 준수(D.2), 경쟁 제품·재판매 금지(D.4), 출력 평가와 사실적 주장의 독립 확인 고지(D.3), 계정 책임(D.5), 개인정보 보호법 준수(D.1)를 요구한다. 약관의 전체 동의 화면은 읽지 못했다.
9. **AI 승급 기준**(Haiku → Sonnet)은 실제 prompt fixture 결과로 정한다. **출시 전 결정(구현 전이 아님)**: 공개 출시에 앞서 월 소멸하는 포함 크레딧 대신 유료 API 크레딧(또는 결제 설정)으로 전환하고, 적용되는 상업 약관·크레딧 약관을 확인하고(포함 크레딧이 상업 서비스에 쓰일 수 있는지는 소유자의 이해일 뿐 공개 페이지로 확인되지 않았다), workspace 지출 한도·커플당 하루 3회·모델 승급 규칙을 정한다. 서버 푸시 필요 여부도 출시 때 정한다.
10. 적용 이력(버전 스냅샷)의 보관 상한·정리 기간과 공간 종료 때 연결 계정/동의 이력의 법적 삭제 범위. 적용된 prompt/message 원문 30일 보관, 취소/만료 미적용 preview 24시간 보관 후 삭제, 종료된 공간 데이터의 내부 보관 30일 뒤 완전 삭제는 기본값이다.
11. **생성 장식(4차 답변, 가정으로 진행)**: 거절·실패가 횟수를 쓰는지(가정: 안 씀, 소유자가 따로 확인하지 않음) · 렌더 이미지 기반 2차 검사 도입 · 신고 처리 담당·응답 시간 · 기준 라이브러리 최종 그림 승인. (결정됨: 방 소품 생성 허용, 홈 커버 사진은 신고 대상 아님, 보관함 상한은 서버 설정값(기본 40 가정); `spec.md` Decided 37~40)(`spec.md` Open Decisions 11~18).
12. **출시 전 확인 추가**: 생성 장식에 대한 Apple·Google 스토어 규칙, Anthropic 사용 정책(2026-11-12 시행 개정판), 약관·개인정보 처리방침, AI 결과물 권리의 법률 검토, 연령 등급 설문(`research.md` 9장, 확인 못한 항목 명시).
13. **계정 삭제(설계됨, 출시 전 확인 남음)**: 7차 답변(결정 41~46)으로 V1(P1, US10)에 설계했다("계정 삭제 (P1, 출시 필수)" 절). 구현 전 준비: ① 카카오 연결 끊기 API 사용 권한과 서버 비밀 키, Apple 로그인 서비스 키(토큰 해제용)와 팀·키 ID 준비(소유자) ② Apple 토큰 해제 API·카카오 unlink의 현재 요청 형식과 이미 해제된 경우의 오류 형태를 공식 문서로 확인(`research.md` 10장의 미확인 항목) ③ 설치된 Supabase Auth 버전에서 세션 무효화 방법(`auth.sessions` 삭제)과 `deleteUser`·Storage 소유자 동작 확인 ④ `aroom.jinjinstar.com/delete-account` 페이지 제작(소유자) ⑤ 출시 전 확인 G18: 처리방침 문구, Apple 심사 메모, Google 데이터 보안 양식, 앱 밖 요청 절차(`spec.md` Open Decisions 26·30). 남은 열린 질문은 유예 삭제·상대 문구 대안·재가입 차단·공간 즉시 완전 삭제·동의 로그 보관·검토 전 신고·내보내기(`spec.md` Open Decisions 23~29).
14. **보관·삭제 안내의 법률 검토와 신고 행 보관**: 개인정보 처리방침·스토어 데이터 안전 입력란에 실제 동작("공간 종료 후 최대 30일 서버 내부 보관 뒤 삭제, 이용자 직접 복구 없음")을 적어야 하는지와 문구, 운영자 지원 복구는 **약속하지 않음**, 신고 행을 완전 삭제 뒤에도 둘지(`spec.md` Open Decisions 21·22). 계정 삭제 때의 즉시 삭제·익명화 항목과 내부 보관 항목의 처리방침 문구도 같은 검토에 들어간다(Open Decisions 30).

## 저장소 구조 제안

```text
apps/mobile/                  Expo 앱 (src/app, src/features, src/scene, src/ui)
packages/scene-contract/      공유 JSON Schema와 순수 검증 규칙
supabase/functions/           AI 제안·세션 안 되돌리기·공간 종료(소프트 삭제)와 완전 삭제 예약 작업·계정 삭제(`account/`, 공급자 해제는 `_shared/providers/`)·초대·생성 장식 보관함·신고 서버 함수
supabase/functions/_shared/reference-library/  기준 라이브러리 번들(design/reference-library에서 빌드 때 복사)
supabase/migrations/          공간·멤버·초대·동의·테마·버전·요청·세션·대화·홈 커버 사진 스키마와 Storage 정책
```

현재 저장소에 애플리케이션 코드가 없으므로 이 구조는 제안이며, 구현 시작 때 저장소 소유자가 확정한다. **구현 태스크 목록은 [tasks.md](./tasks.md)**(DB 테스트용 `supabase/tests/`, `tools/`, `docs/`는 이 구조 밖에 더한 제안)이고 문서 간 일관성 점검은 [analysis.md](./analysis.md)다.

## 범위 간극

초대 수락과 꾸밈 적용은 공유 공간에 저장한다. prompt-session lease는 보통의 동시 편집을 한 owner로 직렬화하고 상대방에게 shared conversation/preview를 Realtime read-only로 전달한다. 유휴 세션은 만료 후 takeover할 수 있다. version compare와 idempotency guard는 경합 시 중복 적용을 막는 서버 최종 안전장치다. 세션 유휴 제한 시간과 점유자의 read-only 화면 표현은 구현 시 조정 가능한 captain decision으로 남긴다.

## 복잡도 추적

헌법 위반 없음. 별도 서비스 경계는 AI 키를 앱 밖에 두고 공유 데이터의 서버 권한을 강제하기 위해 필요하다.

### Invite link implementation (assumptions, 2026-10)
Use Universal Links and Android App Links on the public domain, plus a development custom scheme. Persist a pending code locally until the authenticated join flow consumes it. The static site supplies association files and a localized fallback with no analytics; store destinations remain disabled until known. No deferred-link SDK is included. The owner enables Associated Domains for the development Apple App ID and supplies release signing fingerprints and store URLs before release.
