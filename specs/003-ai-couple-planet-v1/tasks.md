# Tasks: AI Couple Planet V1 (감자별) 슬라이스 계획

**Input**: [spec.md](./spec.md), [policy.md](./policy.md), 디자인 캔버스 V1 보드 `P00`~`P02`, `K01`, `K02`

**구성**: 슬라이스 하나 = PR 하나, 모든 PR의 기준 브랜치는 `v1`(절대 `main` 아님). 각 슬라이스는 앞 슬라이스 위에서 혼자 실행·검증할 수 있게 순서를 정했다. 앞쪽은 AI 없이 확인할 수 있는 것(별을 그리고, 데이터를 공유하고, 놓고, 돌보는 것)이고, 비용·안전이 미정인 AI 생성은 그 위에 붙인다. 각 슬라이스의 기술 계획(데이터 모델·계약)은 그 슬라이스 PR이 이 폴더에 더한다. 이 문서는 순서와 경계만 정한다.

**첫 구현 슬라이스**: **V1-S1 감자별 홈 셸**. 서버 변경 없이 3D 별과 아루미를 그리고 돌리는 화면 하나다. V1의 가장 큰 기술 위험(Expo에서의 3D 렌더링과 기기 성능)을 가장 먼저 실제 기기에서 줄인다.

**모든 V1 슬라이스의 공통 완료 조건(DoD)**:

1. PR 기준 브랜치는 `v1`이다. `main`에 직접 올리지 않는다.
2. V1 기능은 V1 플래그 뒤에 있고 production 빌드에서 꺼져 있다(`V1-NF-01`). V0 화면·V0 동작·`specs/002-*`·`specs/001-*`를 바꾸지 않는다.
3. `corepack pnpm verify`가 통과하고, 마이그레이션·Edge Function을 바꾸면 `corepack pnpm verify:db`도 통과한다.
4. 슬라이스가 다루는 V1 수락 시나리오 ID가 테스트 이름에 있다(V1-S1이 더하는 추적 검사).
5. 화면을 바꾸면 `verify-aroom` 스킬로 Aroom-dev 시뮬레이터 증거를 남기고 design-review 선언을 한다. V1 화면 보드가 있는 화면은 보드와 레이아웃·문구·상태가 같다.
6. 새 문구는 i18n 키로만(ko 원본, en/ja 초안), 3D 장면은 `V1-NF-08` 스타일 규칙을 따른다.
7. 마이그레이션은 머리에 되돌리기·삭제 정책을 적고(`tools/ci/check-migrations.mjs`), 새 공개 함수는 권한 허용 목록 검사(`function_grants.test.sql`)를 통과한다. `v1`에 있는 동안 DB push는 Aroom-dev에만, 슬라이스 PR 병합 뒤 오너 승인으로 한다. Aroom-dev는 V0 preview 빌드와 함께 쓰므로 V1 마이그레이션은 더하기만 하고 V0 테이블·함수의 동작을 바꾸지 않는다. prod push는 `v1`이 `main`에 합쳐진 뒤(S15)에만 한다.
8. 공유 변화(놓기·테마·성장·기념 오브젝트·모습·만들기)는 S2가 만드는 `planet_activity`에 한 줄씩 남긴다. 상대 알림과 추억 모음(S10)이 이 기록을 읽는다.

## 의존 관계

```text
S1 홈 셸 ──► S2 행성 데이터 ──┬──► S3 보관함·기념 오브젝트 ──► S4 배치 편집
                               ├──► S5 돌봄·별조각
                               ├──► S6 포즈·표정·위젯
                               └──► S7 프리셋 테마·성장 단계
S8 생성 제공자 스파이크 (앱 코드와 독립, 언제든)

S3 + S5 + S8 ──► S9 글로 만들기 ──► S10 상대 알림·추억 모음 ──► S15 출시
S11 상호작용·의상 · S12 AI 테마 · S13 사진 · S14 수익화: 결정이 난 것만 S15 전에 넣는다
```

S3·S5·S6·S7은 S2 뒤에 서로 독립이라 병렬로 진행할 수 있다(S6의 `V1-pose`는 `V1-home`에서 연다)(파일이 겹치는 곳은 V1 플래그 묶음과 snapshot 타입뿐이라 먼저 병합된 PR 위에 다시 맞춘다). S8은 앱 코드를 바꾸지 않아 S1과 동시에 시작할 수 있다. S9는 S3(보관함), S5(별조각), S8(제공자 결정)이 모두 필요하다. S4(배치 편집)는 S9 전에 있으면 좋지만 필수는 아니다. S15는 MVP(S1~S10)와 그때까지 결정이 나서 끝난 뒷 슬라이스만 기다린다.

## 디자인 선행 조건

V1 화면 보드는 아직 없다(spec "이 spec이 정하지 않는 것"). S1은 `P01` 스타일 견본과 `P02` 토큰으로 진행한다. S3부터는 해당 화면 보드(`V1-inventory`, `V1-care`, `V1-pose`, `V1-theme`, `V1-create*`, `V1-memories`)가 캔버스에 있어야 보드 일치 기준(DoD 5)을 적용할 수 있다. 보드가 늦으면 그 슬라이스는 데이터·서버 부분만 먼저 내고 화면은 보드가 나온 뒤 다음 PR로 낸다.

**목표**: 제공자를 고를 근거 표를 만든다. 사용자에게 나가는 코드는 없다.

- 후보 2~3개에 같은 입력 세트(가구·식물·음식·건물·기념물 등 20개 안팎, 한국어 설명 포함)를 보내 생성 시간 p50·p90, 1회 비용, GLB 크기·삼각형 수, `P01` 스타일 적합도, 상업 이용 조건, 입력 보관·학습 정책을 잰다.
- 스타일 정리(색을 팔레트로, 광택 제거, 크기 맞춤, 삼각형 줄이기) 방법과 어디서 할지(서버 대 기기)를 함께 시험한다.
- 결과를 이 폴더 `research.md`에 표로 남기고 오너에게 제공자와 생성 상한을 묻는다. 키는 로컬 환경에만 두고 저장소에 넣지 않는다.
